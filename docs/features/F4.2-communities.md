## 1. Purpose

RQ2 asks whether the groups that form through collaboration are the same as genre labels. F4.2 finds communities in the COLLAB graph with weighted Louvain and measures how well they match each artist's primary genre (NMI, PRD §5.5). It also describes the largest communities by their genre mix and best-known members, and checks how stable the partition is. The community of each artist is written back to `:Artist.louvain` (PRD §8.3) for the demo and for later figures.

## 2. What was built

- **`python -m musin.analytics.communities`**: like F4.1, it runs on whatever graph `loaded_graph.json` names, stamps that graph on every row, and has no `--sample` flag.
- **`neo4j/05_communities.cypher`**: Louvain estimate and mutate run, connected components (WCC), the genre list, batched write-back, and the write-back count. It reuses `centrality.degree`, `centrality.stream_property` and `centrality.artists` from `04_centrality.cypher`.
- **Loaded-graph guard** (`analytics.common.check_still_loaded`, now also used by F4.1): after its last Neo4j query a stage re-reads `loaded_graph.json` and discards its results if another import replaced the graph during the run. Two people (or sessions) share one Neo4j database, so this is a real risk.
- **Config keys** (D-034): `analysis.louvain_concurrency`, `analysis.top_k_communities`, `analysis.community_example_artists`.
- **Outputs:** `communities_runs.csv`, `communities_stability.csv`, `communities_sizes.csv`, `communities_top.csv`, and `:Artist.louvain`.
- **16 unit tests**: size-rank relabelling with ties, size buckets, size distribution, NMI/AMI on labelled artists only (perfect and independent cases), stability alignment by artist, the largest-component tie-break, the top-community composition and example artists, the Cypher statements, and the loaded-graph guard.

## 3. How it works

1. **Project** `collab_undirected` (F3.5): one undirected relationship per artist pair, `weight` = shared recordings (D-017, D-028).
2. **Memory guard:** projection plus `gds.louvain.mutate.estimate` must fit `NEO4J_HEAP_SIZE`.
3. **Louvain, 1 + 3 runs** (D-034), each in mutate mode under its own property (`louvain_record`, `louvain_stability_1..3`):
   - the **run of record** at `analysis.louvain_concurrency` = 1. It is reproducible: two runs give identical partitions.
   - **stability runs** at `analysis.concurrency` = 4. Thread scheduling changes the order in which nodes are visited, which is exactly the variation a stability check should probe.
   - Weighted by `weight`; GDS defaults for maxLevels (10), maxIterations (10) and tolerance (0.0001), recorded per run.
4. **Weighted degree** (`centrality.degree`) to choose example artists, and **WCC** to find the largest connected component.
5. **Stream** every property and map GDS node ids to artists with one `MATCH (a:Artist)` query (as in F4.1). Check that every projected artist has a community in every run.
6. **Relabel** the run of record's communities by size: 1 = largest, ties broken by the smallest member `artistId`. GDS's own ids depend on processing order; the size rank does not, so tables, Neo4j and the report use the same numbers.
7. **Write back** `:Artist.louvain` = size rank, in batches of 50,000 with `UNWIND … MATCH (a:Artist {artistId}) SET`. This uses the unique `artistId` constraint's index (F3.5). Then check that every artist has the property.
8. **Guard:** check that `loaded_graph.json` still names the same graph.
9. **Tables** (pandas, all from aggregated or ≤ 1.2 M-row frames):
   - **Per run:** modularity, community count, largest community, share of artists in the top 10, then genre NMI and AMI over labelled artists, both for all artists and inside the largest component.
   - **Stability:** NMI between every pair of runs, over all artists and inside the largest component.
   - **Size distribution** of the run of record in power-of-ten buckets.
   - **The 10 largest communities:** size, labelled share, the dominant genre and its share, the share of each of the 15 parent genres among labelled members, and the 5 members with the highest weighted degree.

**Design choices and alternatives:**

- **Run of record single-threaded, stability at concurrency 4** (D-034). The alternative, three runs at concurrency 4 keeping the highest modularity, gives a different "result" every time the stage runs, which violates RULES §5. Three runs at concurrency 1 would be identical and check nothing. The chosen split keeps the result reproducible and still measures stability.
- **AMI next to NMI.** With ≈ 42,600 communities against 15 genres, NMI is inflated by chance. AMI corrects for that. NMI stays the PRD metric.
- **The largest connected component** (found during this feature). Almost every small community is a whole small connected component (42,227 of 42,562 on the sample; on the full graph, all 71,078 communities outside the largest component are exactly the 71,078 smaller components). Those islands are communities by construction, not something Louvain discovered. The genre comparison inside the largest component measures what RQ2 asks: how the one connected network divides. Over all artists, NMI also counts which island an artist is on. Both views are reported.
- **Write-back via Cypher `UNWIND`, not `gds.graph.nodeProperties.write`,** because the written value is the size rank computed in pandas, not GDS's internal id.
- **Example artists by weighted degree.** They name the community for a reader. Weighted degree is computed on the same projection in the same run, so F4.2 doesn't depend on F4.1 having been run first.
- **Rejected:** Leiden (an alternative community-detection algorithm in GDS). It isn't in the PRD; Louvain is (§5.5).

## 6. How to run

```bash
docker compose exec spark python -m musin.analytics.communities --config config/pipeline.yaml
```

It runs on the loaded graph (for the full graph: `bash neo4j/import_graph.sh full --overwrite` first, then re-import `sample-f0.05` afterwards). Don't run a heavy Spark job at the same time.

Runtime on the reference machine: sample **71–82 s** over three runs (Louvain 4 s single-threaded and 7–10 s per stability run; WCC; write-back 7 s). Full graph (post-G1, 2026-10-20) **246 s**: run of record 20 s, stability runs 13–14 s each, write-back 19 s. (The provisional full graph took 280 s, with a 29 s run of record.)

## 8. Known issues and limitations

- **No community results for the classical-included graph.** D-039 removes classical-primary artists from the main graph, and F4.2 is not run on the `classical` variant (PRD: only F4.1 and F4.3 are). The only view of classical's effect on communities is the comparison with the provisional graph in §7. Spoken-word recordings are still in the graph: that G1 filter is still open (D-040).
- **The descriptions are interpretation.** The "Reading" column and the report's community descriptions are written by us from the example artists and genre shares; only the shares and names are computed.
- **The sample results predate G1.** Its classical communities (orchestras, and composers billed as artists, such as Handel in community 4) are what OD1 / D-039 addressed; they don't exist on the post-G1 main graph.
- **The genre comparison only sees labelled artists** (39.9 % on the sample, 22.0 % on the full graph, F3.1). Unlabelled artists still shape the communities but don't enter NMI/AMI.
- **Primary genre is one label per artist** (PRD §5), while many artists span genres. That caps how well any partition can match.
- **Louvain's resolution limit:** Louvain can merge small, real groups into larger communities. Leiden or a resolution parameter would address this but are outside the PRD.
- **The stability runs' differences** come only from thread scheduling (GDS Louvain has no random seed). This probes processing-order sensitivity, not resampling of the data.
