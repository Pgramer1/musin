## 1. Purpose

Every number in the project has to come from one fixed, trustworthy copy of MusicBrainz. This feature picks that copy (OD6), downloads it, and proves the files are complete and genuinely published by MusicBrainz before any stage reads them. It also records enough metadata (`manifest.json`) for the report and for checking any other copy.

## 2. What was built

- `python -m musin.ingest.download`: downloads the files in `source.files` for `snapshot_date`, verifies them, and writes `manifest.json`. Flags: `--verify-only` (no network for the large files) and `--show-latest` (prints the newest snapshot on the server and the file sizes, without downloading).
- The MusicBrainz data-dump signing public key, committed as `config/musicbrainz-signing-key.asc`.
- Five config changes: `snapshot_date` pinned, plus `source.base_url`, `source.files`, `source.signing_key_file`, and `source.signing_key_fingerprint` (PRD §8.4, D-013), all checked by `REQUIRED_KEYS`.
- `gnupg` in the Spark image ([F1.1 revision](F1.1-dev-environment.md#9-revisions)).
- 9 pytest cases, including the real signed `SHA256SUMS` of the pinned snapshot as fixtures (`tests/fixtures/dumps/`).

## 3. How it works

**What is on the server.** `https://data.metabrainz.org/pub/musicbrainz/data/fullexport/` holds one directory per export, named `YYYYMMDD-HHMMSS`, plus a `LATEST` file. On 2026-10-10 it held only two: `20260930-002222` and `20261007-002147`. Each directory has ten `.tar.bz2` archives, each with a `.asc` signature, plus `MD5SUMS`, `SHA256SUMS`, and their signatures.

**Snapshot choice (OD6).** We pin `20261007-002147`, the latest export when F1.2 ran, as provisionally agreed for OD6. The config value is the whole directory name, not just a date, because the name is the snapshot's unique ID.

**File choice.** Only `mbdump.tar.bz2` (core tables, CC0) and `mbdump-derived.tar.bz2` (tags and genre votes, CC BY-NC-SA 3.0) are needed for PRD §6.2. Rejected: `mbdump-edit` (16 GB of edit history), `mbdump-editor`, `-stats`, `-cover-art-archive`, `-cdstubs`, and the others; no RQ uses them.

**Trust chain.** A checksum alone only proves the file matches a checksum file from the same server. So:

1. Download `SHA256SUMS` and `SHA256SUMS.asc`.
2. Run `gpg --verify` in a **throwaway keyring** that holds only `config/musicbrainz-signing-key.asc`, and require a `VALIDSIG` status line for the pinned fingerprint `D5E63B4BDCCE195642948684B8FC2375C777580F`. That is the key the [MusicBrainz download docs](https://musicbrainz.org/doc/MusicBrainz_Database/Download) name (ID `C777580F`). The key was fetched from `keyserver.ubuntu.com`, and its fingerprint and user ID ("MusicBrainz (MusicBrainz data dump signing key) <support@musicbrainz.org>", RSA 2048, created 2012-09-18, no expiry) were checked before committing it. A throwaway keyring means nothing in a user's own `~/.gnupg` can affect the result, and no trust database is needed.
3. Hash every downloaded file with SHA-256 and compare it with the now-trusted `SHA256SUMS`.

Rejected: verifying each archive's own `.asc`. That is equivalent once the signed `SHA256SUMS` is trusted, and it would mean 2 extra downloads and gpg runs.

**Download.** The downloader uses Python's standard library (`urllib`), with no extra dependency. Each file streams in 8 MB chunks to `<file>.part`, which is renamed only when its size equals the server's `Content-Length`. After a network error it waits `10 × attempt` s and resumes with an HTTP `Range` request (the server sends `Accept-Ranges: bytes`), up to 8 attempts. If the server ignores the range, it starts over. Re-running the command resumes from the `.part` file or skips files already present; the files are still re-hashed, so a re-run is also a full check. Before downloading, it compares the remaining bytes with free disk space and stops if they don't fit. Progress is logged every 30 s.

**Why run it in the container.** The same `docker compose exec spark …` pattern as every stage, with `MUSIN_DATA=/data`, so it writes into the WSL filesystem as UID 1000.

**Manifest.** `manifest.json` lists the snapshot, each file's URL, byte count, and SHA-256, the signing fingerprint, and the time of verification. F1.3 can read it, and the report can cite it.

## 5. Configuration

| Key (`config/pipeline.yaml`) | Value used | Meaning |
|---|---|---|
| `snapshot_date` | `"20261007-002147"` | pinned full export (OD6, D-013) |
| `source.base_url` | `https://data.metabrainz.org/pub/musicbrainz/data/fullexport/` | official MetaBrainz dump server |
| `source.files` | `[mbdump.tar.bz2, mbdump-derived.tar.bz2]` | archives to fetch |
| `source.signing_key_file` | `config/musicbrainz-signing-key.asc` | public key used to verify `SHA256SUMS` |
| `source.signing_key_fingerprint` | `D5E63B4BDCCE195642948684B8FC2375C777580F` | the only key accepted |
| `paths.dumps` | `dumps/` | target is `$MUSIN_DATA/dumps/<snapshot_date>/` |

Not configurable, because they cannot change a result: chunk size 8 MB, 8 attempts, 60 s socket timeout, progress every 30 s (module constants).

## 6. How to run

```bash
# full download + verification (this feature has no sample mode: the dump is the input)
docker compose exec spark python -m musin.ingest.download --config config/pipeline.yaml
# re-check an existing or copied snapshot, without downloading
docker compose exec spark python -m musin.ingest.download --config config/pipeline.yaml --verify-only
# what is the newest snapshot on the server?
docker compose exec spark python -m musin.ingest.download --config config/pipeline.yaml --show-latest
```

Runtime on the reference machine (2026-10-10): full download + verification **757 s** (core 694 s and derived 49 s at ≈ 10.5 MB/s; hashing 9 s); `--verify-only` **8 s**; a re-run with the files already present, 6 s.

## 8. Known issues and limitations

- **The pinned snapshot expires from the server.** Only the two latest weekly exports are kept, so `20261007-002147` will disappear around 2026-10-21. After that, the copy on the reference machine is the only source. Another machine copies `$MUSIN_DATA/dumps/20261007-002147/` from it and runs `--verify-only`, which needs no network. Keep that folder until the project is submitted.
- **The disk check sees the WSL virtual disk.** Inside WSL/Docker, free space shows the virtual disk's maximum size (the log said 1024.2 GB free), not the real space on C:. `setup/preflight.sh` reports the real host-drive figure (330 GB free on 2026-10-10); run it before large downloads.
- **Trust in the key file.** The fingerprint was checked against MusicBrainz's documentation once, by hand. If MusicBrainz rotates its key, verification fails loudly; update both `source.*` key settings together, with a decision entry.
- **A corrupt complete file is not auto-deleted.** If a finished file fails its SHA-256, the run stops; delete the file and re-run. A failed `.part` resumes automatically.
- **License split.** The derived dump (tags) is CC BY-NC-SA 3.0, which is fine for coursework and must be cited (PRD §6.4).
