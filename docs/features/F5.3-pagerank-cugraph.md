## 1. Purpose

F5.2 showed that Neo4j GDS computes PageRank about 120× faster than Spark GraphFrames on the same 4 CPU cores. FR-23 asks for the same comparison on a GPU with RAPIDS cuGraph. The reference machine has one (RTX 4060 Laptop, 8 GB), and CLAUDE.md reserves it for this feature. The question for the report (G4) is how much faster a GPU graph library is than GDS here, and whether it changes the architecture.

## 2. What was built

| Piece | What it is |
|---|---|
| Service `rapids` | GPU container from `rapidsai/base:26.08-cuda12-py3.11` + PyYAML, behind the compose profile `gpu`. It runs as the host user with the image's `conda` group (gid 1001) |
| `python -m musin.benchmark.pagerank_gpu` | cuGraph PageRank on the loaded graph's Parquet, `benchmark.pagerank.repeats` times, each in a fresh process, timed in F5.2's three phases. Saves `run_cugraph_r<n>.json` and `scores_cugraph_r<n>.parquet`, and skips saved repetitions |
| `musin.benchmark.common` | Settings, loaded-graph marker, result folder and the resume helpers (`finished`, `collect`, `write_json`), without PySpark or Neo4j imports, so both containers can use them |
| Changes to F5.2's `musin.benchmark.pagerank` | cuGraph is an optional third engine in all four report tables. `--report` rewrites the report. GDS and GraphFrames also save each repetition at once and resume (`--fresh` discards) |
| 4 new tests (10 in the file) | Resume only for the same graph fingerprint, `collect` order, marker name equal to the import stage's, `read_loaded`, ratios for every engine |

## 3. How it works

1. **Same input and settings as F5.2** (D-042, D-043):
   - **Input:** the graph named in `loaded_graph.json`. cuDF reads its `nodes_artist` and `edges` Parquet, forms the distinct unordered pairs on the GPU (`cupy.minimum/maximum` + `drop_duplicates`), and builds one undirected `cugraph.Graph` edge per pair.
   - **Settings:** damping 0.85, tolerance 1e-7, cap 1,000 iterations. cuGraph raises an error if it doesn't converge.
   - **Check:** the vertex count must equal the artist count.
2. **Same scale:**
   - **Double precision:** each edge gets weight 1.0 as float64. Unit weights leave PageRank unweighted, and float64 makes cuGraph compute in double precision like the other engines.
   - **Rescaling:** cuGraph normalises scores to sum 1, while GDS and GraphX sum to N. With no isolated artists the two forms differ only by the factor N, so the scores are multiplied by 1,135,461.
3. **Phases** (`time.monotonic()`, after a device synchronise where it matters):
   - **load:** read the Parquet, form the pairs, build the graph. This includes creating the CUDA context, because every repetition is a fresh process.
   - **compute:** `cugraph.pagerank` plus `deviceSynchronize`.
   - **output:** copy the 1.1 M scores to the host and write them with PyArrow.
4. **Report:** `musin.benchmark.pagerank --report` in the Spark container reads every engine's saved repetitions. It checks that all of them saw 1,135,461 nodes and 5,727,076 directed edges, then rewrites F5.2's four tables with cuGraph included.

*Rejected alternatives and what didn't work:*
- **cuGraph inside the Spark image.** RAPIDS ships CUDA libraries and its own conda environment of about 17.6 GB; mixing it with PySpark's pinned stack (NFR-01) would be fragile. A separate image behind a profile keeps the main image unchanged.
- **Running as the image's own `rapids` user.** That would leave result files owned by uid 1001 in `$MUSIN_DATA`. Adding the `conda` group to the host user gives access without changing ownership.
- **cuDF's `to_parquet`.** Its GPU-side writer (KvikIO) fails under WSL with `CUDA_ERROR_ILLEGAL_ADDRESS`, even for a 1 M-row test frame written to `/tmp`, and `LIBCUDF_CUFILE_POLICY=OFF` didn't change that. Reading Parquet with cuDF works. Writing via the host with PyArrow costs 0.1 s.
- **cuGraph's default tolerance (1e-5) and cap (100).** Those would make the comparison unequal. The shared values from D-042 are used.

## 5. Configuration

No new keys. F5.3 uses F5.2's: `analysis.pagerank.damping` (0.85), `analysis.pagerank.max_iterations` (1000), `benchmark.pagerank.tolerance` (1e-7), `benchmark.pagerank.repeats` (3), `analysis.top_k_overlap` (100), `analysis.top_k_centrality` (20). `analysis.concurrency` doesn't apply on the GPU and is recorded as `cores: null`. The image version is pinned in `docker/rapids/Dockerfile`.

## 6. How to run

From WSL Ubuntu, repo root. Requirements:
- the NVIDIA driver on Windows and Docker Desktop's GPU support (`docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi` must show the GPU);
- the graph in `loaded_graph.json`;
- F5.2's GDS and GraphFrames results, for the full report.

```bash
docker compose --profile gpu build rapids                    # once; pulls rapidsai/base (5.83 GiB compressed, 17.6 GB on disk)
docker compose stop neo4j
docker compose --profile gpu run --rm rapids python -m musin.benchmark.pagerank_gpu --config config/pipeline.yaml
docker compose exec spark python -m musin.benchmark.pagerank --config config/pipeline.yaml --report
docker compose start neo4j
```

Runtime on the reference machine (2026-10-20): 13 s for three repetitions; the report takes seconds. Using the image means accepting the NVIDIA Deep Learning Container License, which the container prints at start (D-043).

## 7. Verification and results

**Environment:**
- **GPU:** NVIDIA GeForce RTX 4060 Laptop GPU, 8 GB, Windows driver 581.86 (CUDA 13.0 capable).
- **Software:** cuDF and cuGraph 26.08.00, CuPy 14.1.1, Python 3.11.15, in Docker Desktop on WSL2.
- **Graph:** `full`, edges fingerprint `-2227712706449027820962`.

**Checks (all passed):**
- 1,135,461 vertices, equal to the artist count;
- 5,727,076 directed edges (2 × 2,863,538 pairs), equal to GDS and GraphFrames in every repetition;
- converged (cuGraph raises otherwise);
- score sum 1,135,461.0 in every repetition.

**Runtime** (seconds, median of 3 with min–max; [`benchmark_pagerank_summary.csv`](../../reports/tables/benchmark_pagerank_summary.csv)):

| Phase | GDS (4 cores) | GraphFrames (4 cores) | cuGraph (GPU) | cuGraph ÷ GDS |
|---|---:|---:|---:|---:|
| load | 11.8 | 9.5 | **0.78** (0.77–1.42) | 0.07 |
| compute | 3.8 | 469.7 | **0.20** (0.19–0.22) | 0.05 |
| output | 14.7 | 2.4 | **0.10** (0.10–0.10) | 0.01 |
| total | 30.3 | 482.1 | **1.09** (1.06–1.71) | 0.04 |

**Agreement** ([`benchmark_pagerank_agreement.csv`](../../reports/tables/benchmark_pagerank_agreement.csv), repetition 1 of each):

| a | b | Spearman ρ | top-100 Jaccard (common) | max relative difference | median relative difference |
|---|---|---:|---:|---:|---:|
| GDS | GraphFrames | 0.99999 | 1.000 (100) | 1.22 × 10⁻⁶ | 1.22 × 10⁻⁶ |
| GDS | cuGraph | 0.99993 | 1.000 (100) | 2.88 × 10⁻⁶ | 9.8 × 10⁻⁷ |
| GraphFrames | cuGraph | 0.99993 | 1.000 (100) | 2.33 × 10⁻⁶ | 2.9 × 10⁻⁷ |
| F4.1 weighted | cuGraph | 0.887 | 0.563 (72) | 8.07 | 0.265 |

The top-20 lists of all three engines are identical ([`benchmark_pagerank_top.csv`](../../reports/tables/benchmark_pagerank_top.csv)).

**What the numbers show:**

- **All three engines give the same ranking.** The top 100 is identical, ρ ≥ 0.99993 over 1.1 M artists, and every score agrees within 3 × 10⁻⁶ relative. Differences come from each library's stopping rule. ρ is slightly lower with cuGraph than between GDS and GraphFrames, because its stopping point leaves near-tied low scores in a slightly different order. No top rank changes.
- **The GPU is fastest by far.** PageRank on the full graph takes 0.2 s on the GPU, 3.8 s in GDS on 4 cores (19×) and 470 s in GraphFrames (about 2,350×). End to end (read, compute, write) cuGraph needs 1.1 s, against 30 s for GDS, mostly projection and Bolt streaming, and 8 min for GraphFrames.
- **It doesn't change the architecture.** cuGraph covers PageRank and Louvain, and sampled betweenness exists there too. But the project needs Neo4j anyway, for the demo (FR-25/26), Cypher shortest paths (F4.5) and write-back of results as properties (§8.3). And the GPU sits in a 17.6 GB image outside the main stack. At these sizes GDS's runtimes are already seconds to minutes, apart from single-threaded betweenness, which is run that way for reproducibility (D-033) rather than speed. So cuGraph is a measured upper bound for this hardware, not a reason to move P4. The report should present it that way.
- **GPU load is cheap because the input is already in columnar form.** Reading 3.1 M edges from Parquet straight into GPU memory and building the graph takes 0.8 s, including the CUDA context. The first repetition's 1.4 s is a cold start.

**Tests:** 10 in `tests/test_benchmark_pagerank.py` (4 new). The full suite has 248 tests, all passing, and `ruff` is clean. The F5.2 report regenerated through the new resume code is byte-identical in its agreement and summary tables, before cuGraph was added.

## 8. Known issues and limitations

- **GPU against CPU.** A laptop GPU is compared with GDS limited to 4 CPU cores by its Community licence. The result is about this machine.
- **No iteration count** from `cugraph.pagerank`, and its tolerance follows cuGraph's own convergence rule. The score comparison shows the effect, which is below 3 × 10⁻⁶ relative.
- **cuDF's GPU Parquet writer doesn't work under WSL** (KvikIO, `CUDA_ERROR_ILLEGAL_ADDRESS`). Output goes through the host. On native Linux the cuDF writer would likely work, but that wasn't tested.
- **The RAPIDS image is 17.6 GB,** and using it means accepting the NVIDIA Deep Learning Container License. It's optional: nothing else in the pipeline needs it.
- **The CUDA test image** `nvidia/cuda:12.4.1-base-ubuntu22.04` (348 MB), used for the GPU check, was removed after the run.
- **Only PageRank was compared.** Louvain or betweenness on the GPU weren't measured, because FR-23 covers PageRank only.
