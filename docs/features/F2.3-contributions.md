## 1. Purpose

Artist credits (F2.2) only show who is *billed* on a recording. MusicBrainz also records who produced it and who played or sang on it, as typed artist → recording relationships. PRD §8.2 turns those into two directed edge types: `PRODUCED_FOR` (producer → each main artist) and `PERFORMED_FOR` (performer → each main artist), kept apart from credit edges (D-008). This feature extracts the relationships whose link type is in the configurable allowlist (FR-06) and writes them per recording, ready for F3.1 to pair with the main artists.

## 2. What was built

| Piece | What it is |
|---|---|
| `python -m musin.clean.contributions [--sample f]` | Writes `clean/contributions`; logs per-link-type and per-edge-type counts; quality checks |
| `allowlist` | `{link type name: edge type}` from `contributions.produced_for` / `performed_for`; fails on an empty list or a name listed under both |
| `resolve_link_types` | Finds the allowlisted artist → recording (or → release) link types; **fails** if a configured name doesn't exist in the dump |
| `relationships` | Allowlisted rows of an `l_artist_<target>` table |
| `release_to_recordings` | Release → every recording on it (track → medium → release), for OD7 |
| `collapse` | One row per (recording, artist, edge type), with the sorted list of link types behind it |
| 5 tests | Allowlist validation, link-type resolution by target, filtering, release mapping, collapsing |

## 3. How it works

1. **Allowlist → link types.** The config names (`producer`; `performer`, `instrument`, `vocal`) are looked up in `raw/link_type` with `entity_type0 = 'artist'` and `entity_type1 = 'recording'`. Link-type names are not unique across entity pairs (`producer` exists for recordings, releases, works…), so the target is part of the lookup. A missing name stops the stage. This is the verification promised in PRD §8.4 ("verified against the dump in F2.3").
2. **Relationships.** `l_artist_recording` → `link` (to get the link type) → broadcast join with the 4 allowlisted types. In the table, `entity0` is the artist and `entity1` the recording. In sample mode only the sampled recordings are kept.
3. **Release level (OD7), only if `filters.use_release_level_credits`.** The same names are resolved for artist → release. Each release-level relationship is applied to **every recording on that release**, which is how a release credit reads ("produced by X" on the album). Release level is off by default (provisional OD7 value), but the code path exists and was run on the full data (§7), so G1 can flip the key without new code.
4. **Special artists removed** (anti-join with `clean/special_artists`, FR-04): 11,317 relationships, e.g. `[unknown]` as an instrumentalist.
5. **Collapse.** An artist often has several relationships of one edge type on a recording (e.g. instrument + vocal → both `PERFORMED_FOR`). They become one row with `link_types = [instrument, vocal]`, because F3.1 counts distinct shared recordings and must not count one recording twice. `level` is `recording` if any source row is recording-level, else `release`. An artist who both produced *and* performed keeps two rows (different edge types).

**What F3.1 does with it:** an edge from `artist_id` to every **main** artist of the recording in `clean/credits` (PRD §8.2), dropping self-edges (producers who are also the billed artist) and excluded artist types (D-021).

*Rejected:* emitting edges here. Pairing needs the main artists from F2.2 and the edge filters (FR-10/11, D-021), which all belong in F3.1. Keeping `clean/` to one row per relationship fact keeps the layers independent (RULES §6). Also rejected: following the link-type hierarchy (`parent`) automatically, e.g. all children of "performance". The allowlist must stay explicit so a config line, not the MusicBrainz tree, decides what counts.

**Cross-checks against F1.4 (independent code, `reports/tables/profile_contributions.csv`):**

- The four recording-level relationship counts are identical (6,725,798 / 397,922 / 2,447,023 / 2,727,775).
- Recordings with a producer: 1,786,572 vs F1.4's 1,787,112. The 540 difference is recordings whose only producer was a special artist (F1.4 runs before the F2.1 filter).
- OD7: release level adds 629,352 producer recordings and 516,113 performer recordings. F1.4 measured 629,329 and 516,069 not covered at recording level; the small differences are the special-artist filter.
- Sample 0.05: producer coverage 89,415 / 2,025,357 = 4.41 % and any contribution 9.90 %, matching F1.4's full-data shares (4.4 %, 9.9 %).

**Quality checks (stage):** no duplicate (recording_id, artist_id, edge_type); no special artists; edge types only `PRODUCED_FOR` / `PERFORMED_FOR`. Every allowlisted name resolved to exactly one artist → recording link type (141 producer, 148 instrument, 149 vocal, 156 performer).

`pytest`: 81 passed (76 earlier + 5 new); `ruff check` / `ruff format --check` passed.

**For G1:**

- **OD5:** producer credits cover 4.4 % of recordings (1.79 M), with a strong era bias (F1.4).
- **OD7:** release level would add 52.7 % more contribution rows but only 1.7 points of recording coverage (9.91 % → 11.63 %). Most of the added rows repeat an album-wide credit on every track. That inflates edge weights for album producers, because one release-level credit on a 12-track album becomes weight 12 in F3.1.

## 8. Known issues and limitations

- **Coverage bias:** contribution credits exist for about 10 % of recordings, concentrated in well-documented popular releases and in certain eras (F1.4, PRD §6.3). `PRODUCED_FOR` / `PERFORMED_FOR` results describe documentation effort as much as practice.
- **Release-level semantics (if OD7 is switched on):** an album credit applies to every track, which overstates per-track involvement (see above).
- **No contributor filter here** for `Character` artists (D-021) or group members (FR-11); both are applied in F3.1, together with dropping self-edges.
- **Allowlist scope:** `conductor` and `performing orchestra` (1.8 M relationships combined) are excluded by the current config; engineers, arrangers, and remixers too.
- **Link attributes** (which instrument, lead vs backing vocal) are not read; `link_types` keeps only the type names.
