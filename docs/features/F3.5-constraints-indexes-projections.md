## 1. Purpose

After F3.4 the graph is in Neo4j, but it has no constraints or indexes: every lookup by `artistId` scans 1.18 M nodes, and nothing enforces uniqueness. P4 also needs the two projections PRD §5 names:

- **COLLAB** for all four research questions
- **credit-only** for RQ4's sensitivity run

Both must be built exactly as D-017 defines (one undirected relationship per artist pair, weights summed). This feature provides both, proves they contain what the Parquet graph says they should, and confirms before P4 starts that the algorithms fit the 8 GB heap.

## 3. How it works

**Schema ([D-032](../decisions.md#d-032--neo4j-schema-and-the-two-production-projections)).** Three uniqueness constraints and one index, all `IF NOT EXISTS`, so re-running is harmless:

- `artistId`: every P4 lookup, write-back, and report join goes through it.
- `mbid`: reports identify artists by MBID (RULES §6).
- `Genre.name`.
- A range index on `Artist.name`, for name lookups in the demo and in degrees of separation. Names are not unique, so it isn't a constraint.

Creating a uniqueness constraint fails if the imported data violates it, so this is also a final data check. The setup waits for population and requires every index to be `ONLINE` at 100 %.

**Projections.** A single statement builds both, with a parameterised type list.

- **How pairs are formed:** `MATCH (s:Artist)-[r]->(t:Artist) WHERE type(r) IN $types`. Endpoints are put in `artistId` order and weights summed per pair, then `gds.graph.project(…, {undirectedRelationshipTypes: ['*']})`. This is D-017 as verified on the toy graph in F1.5.
- **What the weight means:** with D-028, the summed weight is the number of recordings the two artists share.
- **`collab_undirected`:** `CO_CREDITED + FEATURED + PRODUCED_FOR + PERFORMED_FOR`, i.e. COLLAB.
- **`credit_only`:** `CO_CREDITED + FEATURED`, for the RQ4 sensitivity run. It contains only artists with a credit edge. Contributor-only artists (D-027) aren't in it, because they have no credit relationship. RQ4's agreement statistics on this projection are therefore over a smaller artist set (§8).

**Checks per projection** (expected values from the Parquet edges of the graph named in `loaded_graph.json`):

1. **Heap guard before building.** A Cypher-aggregation projection has no `.estimate`. Instead, `gds.graph.project.estimate` of the *native* projection of the same types (parallel relationships kept, so an upper bound) must be below `NEO4J_HEAP_SIZE`.
2. **Content.**
   - Node count equals the artists with an edge of those types.
   - Relationship count equals 2 × unordered pairs, since undirected pairs are stored both ways.
   - The streamed weight total equals 2 × the summed Parquet weight.
   - The 5 heaviest pairs, with `artistId`s and weights, equal Parquet's.
3. **Memory for P4.** Projection size plus the largest `.estimate` of the four §5.5 algorithms (settings from `analysis.*`) must be below the heap. This is RULES §7's "estimate before running on the full graph", done once for every algorithm before P4.
4. **Cleanup.** Every projection is dropped, and `gds.graph.list()` must be empty afterwards. Projections live on the heap, and P4 builds its own.

Spark computes the expectations first and stops before any projection is built, so Spark and GDS never compete for memory (PRD §7.2).

*Rejected alternatives:*
- **Native projections:** parallel relationships distort betweenness (D-017, measured in F1.5).
- **Keeping projections alive between sessions:** they cost heap and disappear on restart anyway; P4 calls `project()`.
- **A separate projection per edge type:** no research question needs one yet (D-017 leaves type-specific projections to the analyses that need them).
- **Running the constraints by hand:** they would be missing after the next import, because every import replaces the database. The import script now applies them.

Development found two bugs before the first successful run:
- **Name mismatch:** `INDEXES` named the index `artist_name` while the Cypher statement was called `artist_name_index`. The name-consistency test caught it; statement names now equal constraint/index names.
- **Parameter collision:** `Session.run(name, **params)` clashed with the Cypher parameter `$name`. The first live run caught it; the statement argument is now positional-only.

## 5. Configuration

| Key | Value used | Meaning |
|---|---|---|
| `analysis.pagerank.damping`, `analysis.pagerank.max_iterations` | 0.85, 20 | PageRank estimate |
| `analysis.betweenness_sampling_size`, `analysis.random_seed` | 10,000, 42 | betweenness estimate (unweighted, §5.5) |

No new config keys. Projection names and type lists are fixed by PRD §5 and RULES §7, so they are constants (`PROJECTIONS`), not settings.

## 6. How to run

```bash
# normally automatic: the last step of every import
bash neo4j/import_graph.sh sample-f0.05 --overwrite
# on its own (idempotent), against whatever graph loaded_graph.json names
docker compose exec spark python -m musin.gds.setup --config config/pipeline.yaml
# in P4 code
#   from musin.gds.setup import project, drop
#   project(driver, "collab_undirected"); ...; drop(driver, "collab_undirected")
```

Runtime on the reference machine: full graph **72 s** (constraints and indexes 6.4 s; COLLAB built in 15.1 s; credit-only in 8.9 s; the rest is Spark expectations, checks, and estimates). Sample 28–35 s. The whole full import script, now including the setup, took 128 s.

## 7. Verification and results

Runs 2026-10-11, snapshot `20261007-002147`, graph from F3.1 at commit `2ac5547`. The full graph was imported with the updated script (import → 39 checks → setup); then the sample was re-imported the same way, and **Neo4j now holds `sample-f0.05`** with the schema in place.

**Schema:** all three constraints and the `artist_name` index created and `ONLINE` at 100 % on both graphs (6.4 s on the full graph). No uniqueness violation.

**Projections, full graph** (`reports/tables/gds_projections.csv`):

| Projection | Nodes | Relationships (= 2 × pairs) | Total weight (= 2 × Parquet) | Build | Memory |
|---|---:|---:|---:|---:|---:|
| `collab_undirected` | 1,180,939 | 6,602,784 (3,301,392 pairs) | 34,726,004 (17,363,002) | 15.1 s | 193 MiB |
| `credit_only` | 888,062 | 4,641,526 (2,320,763 pairs) | 21,476,750 (10,738,375) | 8.9 s | 145 MiB |

- Every check passed: node count, relationship count, weight total, and the 5 heaviest pairs, all equal to Parquet. The heaviest COLLAB pair is Springsteen–E Street Band, 57,661.
- The COLLAB pair count and total weight also equal the independent exploratory query from the G1 evidence work (3,301,392 pairs, 17,363,002).
- All projections were dropped afterwards (`gds.graph.list()` empty).

**Memory estimates for P4** (full graph, §5.5 settings, `bytesMax`):

| Algorithm | `collab_undirected` | `credit_only` |
|---|---:|---:|
| Weighted degree | 9.4 MB | 7.1 MB |
| PageRank (0.85, 20 iterations) | 28.5 MB | 21.4 MB |
| Louvain | 386.6 MB | 281.2 MB |

**Sample graph:** all checks passed on both runs. COLLAB has 310,253 nodes and 524,330 pairs (total weight 865,430, matching F3.2); credit-only has 209,560 nodes and 321,271 pairs. Projection plus the largest estimate is 0.16 / 0.12 GiB.

**Tests:** `pytest` 155 passed (144 earlier + 11 new); `ruff check` / `ruff format --check` passed; `bash -n neo4j/import_graph.sh` passed.

## 8. Known issues and limitations

- **`credit_only` has fewer artists** (888,062 vs 1,180,939). When RQ4 compares rankings between the two projections, it must restrict to artists present in both, or state the difference.
- **The heap check covers one projection plus one algorithm at a time.** Running several projections at once, or betweenness without sampling, is not covered.
- **Estimates are GDS's own figures,** not measured peaks. P4 should log actual runtimes and memory. Betweenness runtime (not memory) is the known P4 risk (PRD §13).
- **The heaviest-pair check compares the top 5 only.** Totals and counts cover everything else in aggregate.
- **Review:** this doc and the API should be reviewed before they are used in P4.
