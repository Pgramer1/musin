## 1. Purpose

Both members need an identical, pinned environment that runs PySpark and Neo4j + GDS on a Windows 11 laptop without Spark-on-Windows problems (D-007), stays inside the 24 GB memory budget (PRD §7.2), and reads its settings from the two contracts: `config/pipeline.yaml` for anything that changes results, and `.env` for secrets and per-machine values. Every later feature runs inside this environment.

## 3. How it works

```
Windows 11
 └─ WSL2 VM (18 GB cap from .wslconfig) ── shared by Ubuntu and Docker Desktop
     ├─ Ubuntu shell: repo checkout, .env, $MUSIN_DATA=~/musin-data
     └─ Docker engine
         ├─ spark  (musin-spark:f1.1)  /workspace ← repo   /data ← $MUSIN_DATA
         │         Jupyter :8888, Spark UI :4040
         └─ neo4j  (musin-neo4j:f1.1)  /data,/logs ← $MUSIN_DATA/neo4j   /import ← $MUSIN_DATA/import (ro)
                   Browser :NEO4J_HTTP_PORT, Bolt :NEO4J_BOLT_PORT
```

**WSL2 memory cap.** Docker Desktop's WSL2 backend runs inside the same VM as Ubuntu, so `.wslconfig` caps both. Without one, WSL defaults to half the physical RAM: on the reference machine Docker saw 11.5 GiB (`docker info` MemTotal 12,390,588,416 bytes), which cannot hold Neo4j's 8 GB heap + 5 GB page cache. 18 GB leaves about 6 GB for Windows. `.wslconfig` is a per-user Windows file, so the repo ships a template and each member installs it themselves.

**Two services, no profiles.** Both containers may run at the same time. An idle Jupyter server uses little memory, because the Spark JVM only starts when a notebook or stage creates a session, and P4 notebooks need Jupyter and Neo4j together. The PRD §7.2 rule is about *heavy jobs*, so it stays a working rule, stated in the compose file header, not something compose enforces. *Rejected:* compose profiles that only allow one service at a time, which would block the P4 workflow.

**Settings come only from `.env`.** Compose interpolates `${KEY:?message}` for every §8.5 key, so a missing key stops `docker compose` with an error naming it instead of starting with a hidden default (verified, §7). The `spark` container gets the whole `.env` via `env_file`, but `MUSIN_DATA` is overridden to `/data`, its mount point, so code inside the container always sees the same path. Spark shuffle and spill (`SPARK_LOCAL_DIRS`) go to `$MUSIN_DATA/tmp/spark` on the WSL disk, not into the container's writable layer.

**Spark image.** It is built from `python:3.11.16-slim-bookworm` (RULES §5 requires Python 3.11) plus Debian's OpenJDK 17, which Spark 3.5 supports. The `pyspark` wheel bundles the Spark jars, so no separate Spark download is needed. `src/` is on `PYTHONPATH`, so `python -m musin.<stage>` works on the mounted repo without an install step. The container runs as UID 1000 (the first WSL user) so files it writes into `$MUSIN_DATA` and the repo belong to the host user. *Rejected:* `quay.io/jupyter/pyspark-notebook`, whose Python version follows the Jupyter stack (not 3.11) and which ships far more than we need. pandas/numpy are pinned to 2.2.3/1.26.4 because PySpark 3.5 is built against pandas 2 / numpy 1.

**Neo4j image and GDS pinning.** The first attempt used the stock `NEO4J_PLUGINS='["graph-data-science"]'` mechanism. Its log showed that it fetches `versions.json` and re-downloads the newest compatible GDS on **every** container start, including restarts. The GDS version could therefore change between runs without anyone noticing (breaking NFR-01), and startup needs the internet. `docker/neo4j/Dockerfile` instead `ADD`s the GDS 2.13.12 jar (the version `versions.json` maps to Neo4j 5.26.30) with `--checksum=sha256:246e3fbb…`, so the build fails if the file ever changes. Neo4j 5.26 is the 5.x LTS line, matching PRD §7.1 "Neo4j 5". Anonymous usage reporting to Neo4j is switched off (`dbms.usage_report.enabled=false`); with the default settings, the first start logged that usage data was being sent.

**Neo4j data location.** The store and logs live under `$MUSIN_DATA/neo4j/`, and `$MUSIN_DATA/import` is mounted read-only at `/import` for `neo4j-admin database import` in F3.4. Keeping them under the data root keeps every large file in one place outside the repo, and `docker compose down -v` cannot delete them.

**Ports and Jupyter authentication.** Jupyter (8888) and the Spark UI (4040) are fixed in `docker-compose.yml`, and Jupyter runs **without a token**; this was the team's choice, recorded in [D-012](../decisions.md#d-012--fixed-jupyterspark-ports-jupyter-without-a-token). To keep that safe, **every** published port, Neo4j's included, is bound to `127.0.0.1`, so nothing is reachable from the network. *Rejected (by the team):* adding `JUPYTER_PORT`, `JUPYTER_TOKEN`, and `SPARK_UI_PORT` to the §8.5 `.env` contract.

**Config loader.** `REQUIRED_KEYS` mirrors the PRD §8.4 key list. `load_config()` checks that every key is present and non-null (only `snapshot_date` may be null until F1.2), and `Config.get("a.b.c")` raises `ConfigError` naming the key and file. Example: deleting `filters.max_credit_size` gives `ConfigError: Missing config key 'filters.max_credit_size' in …/pipeline.yaml`. New keys are added to `REQUIRED_KEYS` in the PR that introduces them.

**Environment check.** `musin.envcheck` loads the config, confirms the five layer directories exist, starts Spark through `get_spark()`, logs the Spark, Python, and Java versions, core count, and driver memory, writes 1,000,000 rows to Parquet under `$MUSIN_DATA/tmp/envcheck`, reads them back with a `groupBy`, checks the count, and deletes the files. It exits non-zero on the first failure.

`config/pipeline.yaml` is created with every value exactly as in PRD §8.4 draft v1; none of them is used yet. `.env` keys (PRD §8.5):

## 6. How to run

One-time, in Windows PowerShell:

```powershell
wsl --install -d Ubuntu-24.04                            # creates your Linux user
Copy-Item setup\wslconfig.example $env:USERPROFILE\.wslconfig
wsl --shutdown                                           # then restart Docker Desktop
```

Then in Docker Desktop, go to Settings → Resources → WSL integration and enable the Ubuntu distro.

In the Ubuntu shell, from the repo root:

```bash
cp .env.example .env                     # set MUSIN_DATA=/home/<you>/musin-data and NEO4J_PASSWORD
bash setup/preflight.sh                  # checks the machine, creates $MUSIN_DATA tree
docker compose build
docker compose up -d                     # Jupyter http://localhost:8888, Neo4j http://localhost:7474
docker compose exec spark python -m musin.envcheck --config config/pipeline.yaml
docker compose exec spark pytest
```

Runtime on the reference machine: Spark image build 154 s (cold), Neo4j image build 15 s; `envcheck` 9 s wall time from WSL Ubuntu (Parquet round trip 7.8 s); Neo4j start to first query 12 s.

## 8. Known issues and limitations

- **Manual system steps.** Installing Ubuntu, `.wslconfig`, and Docker WSL integration are done by each member by hand (§6); the repo cannot do them.
- **Free-space numbers inside WSL are misleading.** `preflight.sh` reported 955 GB free and `envcheck` 1024 GB, but those are the *maximum size* of WSL's/Docker's virtual disks. The real limit is free space on the Windows drive that holds them (C:, ≈ 364 GB free on 2026-10-10). Since the F1.2 revision, `preflight.sh` reports the free space of the Windows drive (`/mnt/c`) instead; `musin.ingest.download`'s own disk check still sees the virtual size.
- **Neo4j files are owned by UID 7474.** `$MUSIN_DATA/neo4j/data` and `logs` belong to the container's `neo4j` user, so deleting them from WSL (e.g. to reset the database or password) needs `sudo`.
- **Neo4j password is fixed at first start.** `NEO4J_AUTH` only applies when the store is created; changing `NEO4J_PASSWORD` later has no effect until `$MUSIN_DATA/neo4j/data` is reset or the password is changed in Cypher.
- **Jupyter has no token (D-012).** Any process on the same machine can reach Jupyter and run code with access to `$MUSIN_DATA` and the repo. This is acceptable only because the port is bound to `127.0.0.1`. Never change the binding to `0.0.0.0`.
- **Fixed ports 8888 / 4040.** If another program already uses either port, `docker compose up` fails and the mapping must be edited locally (D-012).
- **UID 1000 assumed.** If `id -u` in WSL is not 1000, files written by the container are owned by another user. Rebuild with `--build-arg HOST_UID=$(id -u)`; `preflight.sh` warns about this.
- **Repo on `/mnt/c`.** Working from the Windows checkout through `/mnt/c` is fine for code, but slower for file-heavy operations; `MUSIN_DATA` must never be there (`preflight.sh` rejects it).
- **Concurrency is a working rule, not enforced.** Nothing stops a heavy Spark job and a heavy GDS algorithm from running together and exceeding 18 GB.
- **Spark event logs** (NFR-04, for benchmarks) are not configured yet; F5.1 adds them.
- **Image downloads:** a cold build pulls the base images and the 64 MB GDS jar, so it needs internet access once.
