## 1. Purpose

RQ4 asks who is most central in the collaboration network and whether different notions of "central" agree. F4.1 computes three measures on the COLLAB projection (PRD §5): weighted degree (how much an artist collaborates), PageRank (collaborating with well-connected artists) and betweenness (sitting on shortest paths between otherwise distant parts of the graph). It measures their agreement with Spearman ρ and top-100 Jaccard overlap, and repeats everything on the credit-only projection as the PRD's sensitivity check. The scores are written back to `:Artist` (PRD §8.3), and F4.3 needs the betweenness for its bridge score `B_i = D_i × percentile_rank(betweenness_i)`.

## 2. What was built

- **`python -m musin.analytics.centrality`**: one command, no `--sample` flag. It analyses whatever graph `$MUSIN_DATA/neo4j/loaded_graph.json` says Neo4j holds (Community Edition has one database, RULES §7) and stamps that graph's name and edges fingerprint on every output row.
- **`neo4j/04_centrality.cypher`**: estimates, the three algorithms in mutate mode, streaming, write-back, and the write-back count check.
- **`musin.analytics.common`**: shared P4 plumbing: the loaded-graph marker, where result tables go, and the CSV writer.
- **Config keys** (D-033): `analysis.concurrency`, `analysis.betweenness_concurrency`, `analysis.top_k_centrality`, and `analysis.pagerank.max_iterations` changed from 20 to 1000.
- **Outputs:** `centrality_top.csv`, `centrality_agreement.csv`, `centrality_runs.csv`, plus the `:Artist` properties `degreeWeighted`, `pagerank`, `betweenness`.
- **11 unit tests** (`tests/test_analytics_centrality.py`): top-k tie-breaking, Jaccard, Spearman with ties, the agreement and cross-projection tables, results paths, the loaded-graph guard, and that every Cypher statement exists and betweenness is unweighted and single-threaded.

## 3. How it works

For `collab_undirected` and then `credit_only`:

1. **Project** with `musin.gds.setup.project()` (F3.5, D-017/D-032). It builds one undirected relationship per artist pair, whose `weight` is the number of shared recordings (D-028). A leftover projection of the same name is dropped first.
2. **Memory guard** (RULES §7): `.estimate` for each algorithm. Projection size plus the largest estimate must be below `NEO4J_HEAP_SIZE`, or the stage stops.
3. **Run the algorithms in mutate mode** with the §5.5 settings:
   - **Weighted degree:** `gds.degree`, `relationshipWeightProperty: 'weight'`. On an undirected projection each pair counts once, so the score is the artist's total shared recordings.
   - **PageRank:** weighted, damping 0.85, run until GDS's tolerance (1e-7) is reached, with at most 1000 iterations. A run that does not converge fails the stage (D-033).
   - **Betweenness:** **unweighted**, because GDS reads weights as distances (PRD §5.5). It samples 10,000 source nodes with seed 42, single-threaded (D-033). Scores are not rescaled to the full number of sources; only ranks and percentiles are used downstream.
4. **Stream** each score with `gds.graph.nodeProperty.stream` and join them on GDS's node id. The node id is mapped to `artistId`, name, type and primary genre with one `MATCH (a:Artist)` query. This is cheaper than calling `gds.util.asNode` on every row of a 1.2 M-row stream.
5. **Check** the scores: one score per projected artist, no missing values, and Σ weighted degree = Σ relationship weight of the projection (each pair is stored in both directions, so this is 2 × the shared recordings).
6. **Write back** (COLLAB only) with `gds.graph.nodeProperties.write`, then check that every `:Artist` carries all three properties. Every artist is in COLLAB (§8.3), so this must hold exactly. `credit_only` scores are not written back, because §8.3 has one property per measure and it belongs to COLLAB.
7. **Drop** the projection, even when a step fails (`finally`).

Then, in pandas:

- **Top-k** (`analysis.top_k_centrality` = 20) per projection and measure. Ties are broken by `artistId` ascending, so the lists and the top-100 sets are deterministic.
- **Agreement** per pair of measures on each projection: Spearman ρ over all artists in that projection (Pearson correlation of average ranks, so the many zero-betweenness ties share a rank), and the Jaccard overlap of the top-`analysis.top_k_overlap` (100) sets.
- **Across projections** (sensitivity): for each measure, ρ over the artists present in both projections, and the Jaccard overlap of each projection's own top 100, which are the lists a reader would compare.

**Design choices and alternatives:**

- **Mutate, then stream, instead of stream mode per algorithm.** Mutate returns each algorithm's statistics (PageRank's `ranIterations` and `didConverge`), which stream mode does not. It also lets one `nodeProperties.write` write all three COLLAB scores at once. Running stats and stream mode separately would compute PageRank twice.
- **No Spark.** The computation happens in GDS. The per-artist frames come from Neo4j (≈ 1.2 M rows × a few columns on the full graph, well within the container's memory), not from a Spark `.collect()`. Spark stays idle, as PRD §7.2 requires when Neo4j does heavy work.
- **Results location.** For the full graph the tables go to `reports/tables/` (committed, report-bound). For a sample they go to `$MUSIN_DATA/sample/f<x>/reports/tables/`, next to the sample's other layers (D-019), so development runs never overwrite report tables.
- **Betweenness concurrency 1, not the shared 4.** It is the only reproducible setting (D-033, measured below). The rejected alternatives were: concurrency 4 with the run-to-run variance documented (fastest, but the top 20 changes between runs), and concurrency 1 with 5,000 samples (half the runtime, but a coarser approximation than the PRD's 10,000).
- **PageRank to convergence instead of 20 iterations.** At 20 iterations the top-20 and top-100 lists differed from the converged ones (D-033). Convergence costs 112 iterations, under 2 s on the sample.

## 6. How to run

```bash
# whichever graph is loaded: the sample (default dev graph, D-031) ...
docker compose exec spark python -m musin.analytics.centrality --config config/pipeline.yaml
# ... or the full graph: import it first (replaces the sample), then run the same command
bash neo4j/import_graph.sh full --overwrite
docker compose exec spark python -m musin.analytics.centrality --config config/pipeline.yaml
bash neo4j/import_graph.sh sample-f0.05 --overwrite    # give the dev graph back
```

Don't run a heavy Spark job at the same time (PRD §7.2).

Runtime on the reference machine:

- **Sample:** **815–891 s** over two runs (betweenness 553–588 s on COLLAB and 224–266 s on `credit_only`).
- **Main full graph** (`full`, 2026-10-19/20): GDS compute time was **5,774.6 s** for betweenness on COLLAB and **3,864.4 s** on `credit_only`, and 4.7 s and 3.3 s for PageRank (`centrality_runs.csv`). The stage's wall time was 24,750 s, but the machine slept for about 4.2 h during the `credit_only` betweenness step: the log timestamps around that step span 18,850 s for 3,864 s of compute. Without the sleep the run took about 9,765 s (2.7 h).
- **Variants** (no sleep): `full-characters` 11,513 s (betweenness 6,990.9 s and 4,556.0 s), `full-classical` 11,088 s (6,555.2 s and 4,466.4 s). The provisional run of 2026-10-13, on the graph `full-classical` now reproduces, took 11,029 s.

Main-graph betweenness on COLLAB took 9.8–10.4× the sample's time, about twice the 5.1× that scaling by graph size (nodes + relationships, as in D-033) suggests. A likely reason (not measured): each sampled source's search covers its connected component, and the largest component holds 83 % of the main graph's artists (945,860 of 1,135,461) but 62 % of the sample's (F4.2).

- **Weighted degree and PageRank are unchanged:** their top-20 lists are identical in set and order on both projections, and so are the 4 top-100 Jaccard values that involve only these two measures.
- **Sampled betweenness is not:**
  - COLLAB top 20: 16 of 20 artists shared (Jaccard 0.667), in a different order. Vineyard Music fell from #4 (93.9 M) to outside the top 20 (2.8 M), a factor of 34.
  - `credit_only` top 20: the same 20 artists in a different order.
  - Of the 40 COLLAB artists in both runs' top lists, 31 have betweenness within ±15 % of the earlier value; the rest range from ×0.58 (Avi Rosenfeld) to ×1.92 (Stephen King), plus Vineyard Music's ×0.03.

- **Likely cause (not verified):** the Neo4j CSV export writes artist rows without sorting them (`src/musin/export/neo4j_csv.py`: `coalesce` without `orderBy`), so a rebuild can import artists in a different order and give them different internal node ids. The seeded sampler then picks a different set of 10,000 source nodes. D-033's reproducibility (identical results for repeated runs) holds within one import, not across re-imports.
- **Consequence:** betweenness ranks and percentiles over all artists are stable, but the exact membership and order of a betweenness top 20 carry real sampling error. Report ranks and percentiles, and don't over-read single positions in the top 20. The same noise is part of every betweenness comparison between graphs, including the Character variant below.

## 8. Known issues and limitations

- **Spoken word is still in the graph.** Its filter is an open G1 item (g1-scope-gate.md §2.1, §4). Until it is decided, audiobook and audio-drama credits shape weighted degree: 4 of the COLLAB top 10 and 8 of the `credit_only` top 10 (§7). They would also enter RQ1's bridge lists.
- **Other artefacts in the weighted rankings** (Springsteen's live archive, g1-scope-gate.md §2.3; labels credited as artists, such as Vineyard Music, F4.6) are scope questions, not F4.1 bugs. Classical is out of the main graph since D-039 and is analysed in the `full-classical` variant.
- **The sensitivity runs** (`full-characters`, PRD §5 RQ4; `full-classical`, D-039) are done on the full variants (§7). Each replaces the loaded graph, so run them before the main graph's P4 stages, or re-run those afterwards.
- **Betweenness is approximate** (10,000 sampled sources) and unweighted. Scores are comparable within a run, not across graphs of different size. Only ranks and percentiles should be reported.
- **Betweenness varies across re-imports.** Two runs on the same graph content, imported separately, shared only 16 of the COLLAB betweenness top 20 (Jaccard 0.667), and single scores moved by up to a factor of 34 (Vineyard Music); ρ moved only in the 4th decimal (§7). D-033's reproducibility holds within one import. The likely cause is that the CSV export does not sort artist rows, which changes the internal node ids that the seeded sampler draws from (not verified). Treat single positions in a betweenness top 20 as uncertain.
- **Single-threaded betweenness is slow:** 1.6 h (5,774.6 s) on the main COLLAB graph and 1.1 h (3,864.4 s) on `credit_only` (D-033). A full F4.1 run takes about 2.7 h on the main graph and about 3.1–3.2 h on the variants. Keep the machine awake, or GDS pauses with it: sleep added hours to the wall time on 2026-10-12 and about 4.2 h on 2026-10-19/20.
- **`credit_only` holds fewer artists** (209,560 of 310,253 on the sample; 852,691 of 1,135,461 on the main full graph, F3.5), so cross-projection ρ is computed on the common artists only.
- **`id(a)` is deprecated** in Neo4j 5. It is used once to map GDS node ids to artists, because GDS node ids are exactly these ids. The deprecation notice is silenced in the stage's logging. If a later Neo4j version removes `id()`, switch to `gds.util.asNode`.
