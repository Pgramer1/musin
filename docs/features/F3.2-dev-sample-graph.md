## 1. Purpose

The Neo4j/GDS analyses (P4) are developed before the full graph is loaded (M3, Oct 24). That needs a small graph that has the exact §8.1 shape, is built by the same code as the full graph, is identical on every machine, and runs on a smaller laptop (NFR-05). FR-12's sample mode already exists stage by stage: every recording-level stage takes `--sample <f>` and samples by hashed recording id (F2.2–F2.4, F3.1; D-019). What was missing is one command that builds the whole sample chain, a way to *prove* two builds are identical, and a statement of what the sample does and doesn't preserve.

## 2. What was built

| Piece | What it is |
|---|---|
| `python -m musin.graph.sample --sample f` | Runs `clean.credits` → `clean.contributions` → `clean.years` → `graph.build` with fraction *f*, then writes a manifest and the sample-vs-full comparison |
| `fingerprint` | Row count + order-independent content hash of a table: Σ `xxhash64(row)` as an exact `decimal(38,0)` |
| `graph_profile`, `degree_quantiles` | Structural metrics of one graph build (sizes, type mix, label coverage, degree quantiles, decade weight shares) |
| `comparison_rows` | Full value, sample value, and their ratio per metric |
| `repo_commit` | Commit of the checkout, read from `.git` (the Spark image has no `git` binary) |
| `$MUSIN_DATA/sample/f0.05/graph/_manifest.json` | Fraction, build time, commit, every result-changing config section, stage runtimes, row counts and fingerprints |
| `reports/tables/sample_f0.05_vs_full.csv` | The comparison (§7) |
| 5 tests | Fingerprint order/partition independence and sensitivity, profile metrics on a 4-artist graph, comparison rows, commit lookup (loose and packed refs) |

## 3. How it works

1. **Preconditions.** The artist-level tables are not sampled (D-019) and must exist in the full clean layer: `artists`, `special_artists` (F2.1), `artist_genres`, `artist_primary_genre` (F2.5). If one is missing, the command stops and names the stage to run.
2. **Chain.** It calls each stage's existing `run(cfg, sample)`, so there is no second implementation that could drift. Each stage writes under `$MUSIN_DATA/sample/f<f>/` and stops its SparkSession; the next stage starts a fresh one in the same JVM. All recording-level stages are re-run, not only `graph.build`, so a config change (featuring pattern, contribution allowlist, OD7) can never leave a stale sample `clean/` behind.
3. **Manifest.** Each graph table gets a row count and a fingerprint: the sum over all rows of `xxhash64` of every column, summed as `decimal(38,0)` so it cannot overflow. A sum is independent of row order and partitioning, so two builds are identical exactly when the fingerprints match (barring a 64-bit hash collision). The manifest also copies every config section that changes results (`snapshot_date`, `filters`, `credits`, `contributions`, `genres`, `years`) and the commit. Spark ignores files starting with `_`, so the manifest can sit in the graph folder.

   This gives F3.4 and P4 a way to note *which graph* a result came from (RULES §7): quote the `edges` fingerprint.
4. **Comparison.** If the full graph exists, both builds are profiled with the same function and written side by side. Degree = distinct collaborators over all edge types, i.e. the COLLAB pairs (D-017). The percentiles are exact, because `percentile_approx` with 1 % rank accuracy returned the maximum as p99 on the full graph.

*Rejected alternatives:*
- **Comparing row counts between runs.** Counts can match while contents differ.
- **A sorted-file checksum.** That needs a global sort and depends on Parquet encoding details.
- **Sampling artists or ego-networks instead of recordings.** That would keep degree structure better, but it is a different sampling unit from FR-12 ("by hashed recording id") and from every existing stage.
- **Writing the D-021 sensitivity build (Characters included) here.** D-021 left its storage to "F3.2/F4.1". It needs a second config, and only F4.1 consumes it, so it stays with F4.1 ([D-029](../decisions.md#d-029--dev-sample-graph-fraction-005-identified-by-content-fingerprints)).

## 6. How to run

```bash
# after F2.1 and F2.5 have run in full mode
docker compose exec spark python -m musin.graph.sample --config config/pipeline.yaml --sample 0.05
# on an 8 GB machine
docker compose exec -e SPARK_DRIVER_MEMORY=4g spark python -m musin.graph.sample --config config/pipeline.yaml --sample 0.05
```

Runtime on the reference machine: **98 s** with a 12 GB driver (credits 20 s, contributions 8 s, years 20 s, graph 39 s, plus the comparison) and **94 s** with a 4 GB driver. There is no separate full mode: the full graph is `python -m musin.graph.build` (F3.1).

| Weight share CO_CREDITED / FEATURED / PRODUCED_FOR / PERFORMED_FOR | 0.539 / 0.080 / 0.138 / 0.244 | 0.542 / 0.080 / 0.138 / 0.239 | 1.01 / 1.01 / 1.01 / 0.98 |
| Edge share FEATURED | 0.207 | 0.115 | 0.55 |
| Nodes with a primary genre | 23.4 % | 39.9 % | 1.70 |
| Nodes with primary genre classical | 2.2 % | 5.7 % | 2.59 |
| Edges labelled at both ends | 35.2 % | 41.4 % | 1.17 |
| Edges with weight 1 | 56.1 % | 76.2 % | 1.36 |
| Degree mean / p50 / p90 / p99 / max | 5.59 / 2 / 11 / 62 / 2,269 | 3.38 / 1 / 7 / 30 / 881 | 0.60 / 0.5 / 0.64 / 0.48 / 0.39 |
| Weight share 1960s / 1990s / 2010s | 0.0167 / 0.1571 / 0.2771 | 0.0168 / 0.1559 / 0.2807 | 1.01 / 0.99 / 1.01 |

How to read this:

- **Weight-based quantities transfer.** Total weight is 0.0498 of the full graph, matching the 5 % fraction, because weight counts recordings. Every edge type's weight share and every decade's weight share from the 1930s on is within 6 % of the full value (most within 2 %). Ratios built from weights, such as RQ3's featuring share, should therefore come out close on the sample.
- **Count- and degree-based quantities do not.** A sampled recording keeps all its artists, but an edge of weight 1 survives with probability 0.05. Well-connected, well-documented artists therefore survive much more often than peripheral ones:
  - genre-labelled nodes 1.7× and classical nodes 2.6× over-represented
  - degrees and the FEATURED edge share (mostly one-off guest spots) shrink.

  Centrality rankings, community sizes, and RQ1's diversity scores on the sample are useful for developing and debugging code, **not** as estimates of the full results.

`pytest`: 110 passed (105 earlier + 5 new); `ruff check` / `ruff format --check` passed. The comparison test caught a null-handling bug during development: unlabelled artists were dropped from the classical share instead of counting as non-classical.

## 8. Known issues and limitations

- **Sampling bias** (above): the dev graph over-represents hubs, genre-labelled artists, and classical; it is a development graph, not a scaled-down copy.
- **The manifest records `HEAD`**, not uncommitted changes. Builds made from a dirty working tree carry the last commit's hash; the fingerprints still identify the content exactly.
- **NFR-05 is checked through the driver-memory setting only**, not on an actual 8 GB machine.
- **Artist-level stages have no sample mode** (as in P2): a small machine still needs the full `clean/artists` and genre tables, which are small (≈ 190 MB) and can be copied from the reference machine.
- **Neo4j loading of the sample graph** is F3.4. M2 ("sample graph loaded in Neo4j") completes there.
