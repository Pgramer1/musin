## 1. Purpose

MusicBrainz uses placeholder "artists" such as `[unknown]`, `[no artist]`, and Various Artists for credits that have no real performer. They sit on hundreds of thousands of recordings, so in a collaboration graph they would become fake super-hubs and connect unrelated artists. F1.4 found `[unknown]` to be the largest recording hub (225,951 recordings, 1,769 collaborators). FR-04 requires excluding them everywhere downstream. This feature defines exactly which artists they are, in a committed file verified against the dump, and produces the typed `clean/artists` table that every later stage uses as its list of allowed artists.

## 3. How it works

### 3.1 Which artists are special

The list was built from the dump, not from memory. An exploration over `raw/artist` (with distinct-recording counts) looked at three signals: names in square brackets (465 artists, 408 on at least one recording), the MusicBrainz disambiguation comment, and the reserved low IDs. The rule:

1. **MusicBrainz marks it itself.** The artist's comment says "Special Purpose Artist", case-insensitive (12 artists): `[unknown]`, `[no artist]`, `[language instruction]`, `[dialogue]`, `[traditional]`, `[anonymous]`, `[theatre]`, `[Disney]`, `[data]`, `MusicBrainz Test Artist`, `[church chimes]`, `[unknown animal]`. All are type `Other`.
2. **Reserved IDs:** `1` Various Artists (the compilation placeholder; its comment is "add compilations to this artist") and `2` Deleted Artist (0 recordings, listed for completeness).
3. **`[mechanical instruments]`** (type `Other`, comment "music boxes, mechanical harmoniums, clocks, etc", 458 recordings): a sound-source placeholder, not a collaborator.

*Left in, deliberately:*

- Real artists who happen to be called "Anonymous", "Unknown", or "Various Artists" (e.g. a German techno producer whose comment says "DO NOT add compilations"). They have their own MBIDs and are genuine.
- `No Artist` (id 2520347), whose comment says "NOT a Special Purpose Artist".
- Bracketed names without the MusicBrainz mark, which are mostly real acts (`[Alexandros]`, `[re:jazz]`, `[dunkelbunt]`).
- Type-`Other` bracketed names that are labels or real projects (`[distatix]`, `[MANA: :DRAIN]`).

Ambiguous unmarked placeholders such as `[blank]` (555 recordings, no type) and `[announcer]` (67) were also kept. See §8.

*Rejected:* a name pattern (`^\[.*\]$`) as the filter. It would drop about 400 real artists and still miss Various Artists. Also rejected: matching by name at run time. Names are not unique ("Anonymous" × 10+), and MBIDs are stable across snapshots.

**Verified against the dump.** The file carries the name next to each MBID. `resolve_special_artists` fails the stage if an MBID is absent from `raw/artist` or if its name there differs, so a typo or a renamed artist cannot silently filter nothing.

### 3.2 The cleaned artist table

`clean_artists` anti-joins the special IDs (broadcast, 15 rows), joins `artist_type` (broadcast) and `area`, and outputs the PRD §8.1 column names and types, so F3.1 can build `nodes_artist` from it directly:

| Column | From | Rule |
|---|---|---|
| `artist_id` | `artist.id` (int) | widened to **long** (§8.1; raw keeps Postgres types, D-014) |
| `mbid` | `artist.gid` | as is |
| `name` | `artist.name` | as is: the profile found no null, blank, or untrimmed names |
| `disambiguation` | `artist.comment` | null when empty. Not a §8.1 column; kept so reports and validation (F4.6) can tell homonyms apart |
| `artist_type` | `artist_type.name` | null when unknown (681,528 artists) |
| `area_name` | `area.name` | null when unknown |
| `begin_year` | `artist.begin_date_year` | **null if later than the snapshot year**; historical years are kept |

**Why null future years.** 25 artists have a begin year after 2026 (maximum 4428). That is impossible at snapshot time, so it is an entry error, and the null is honest. Years ≤ 0 are kept, because MusicBrainz stores historical people (Ηράκλειτος, −535; Marcus Aurelius, 121). Some year-0 values are probably errors, but there is no safe rule to separate them, and `begin_year` feeds no metric (it is a display property). The threshold is the snapshot year from `snapshot_date`, so there is no new parameter.

**The downstream contract.** `clean/artists` *is* the allowed artist set. F2.2 (credits), F2.3 (contributions), and F2.5 (genres) must drop rows whose artist is not in it. Because the excluded set is tiny, the cheap way is an anti-join on the broadcast `clean/special_artists`. F2.2 decides how removing a placeholder from a credit affects featured-artist detection (e.g. `[unknown] feat. X`).

**No `--sample`.** The artist table has 3 M rows and the stage takes 18 s. Sampling is defined by hashed recording ID (FR-12) and happens in the stages that read recordings; they all need the full artist list.

**Worked example** (from the tests):

| raw `artist` row | → `clean/artists` |
|---|---|
| id 1 Various Artists | removed (special) |
| id 4 Massive Attack, type 2, area 221, comment `""`, 1988 | 4, Massive Attack, `disambiguation` null, Group, United Kingdom, 1988 |
| id 5 Heraclitus, −535 | `begin_year` −535 (kept) |
| id 6, area 999 (no match), 4428 | `area_name` null, `begin_year` null |

```bash
docker compose exec spark python -m musin.clean.artists --config config/pipeline.yaml
```

Full mode only (§3.2). Runtime on the reference machine: **18 s** in the stage (20.6 s wall time including JVM start).

## 8. Known issues and limitations

- **Unmarked placeholders stay in.** `[blank]` (555 recordings, no type, comment `s00000`), `[announcer]` (67), `[redacted]` (58), and `[Indistinct Chatter]` (24) look like placeholders, but MusicBrainz doesn't mark them, and the rule keeps the list to evidence-backed entries. They are small enough not to become major hubs; the F3.3/F4 top-10 spot checks (PRD §5.6) should flag any that do.
- **The list is tied to MBIDs.** If MusicBrainz adds a new special-purpose artist in a later snapshot, it is not filtered until it is added to the CSV. The name check catches renames but not additions.
- **`begin_year` ≤ 0** is kept and includes some probable entry errors (several modern artists with year 0). It is a display property only.
- **The impact counts are credit-level.** The recording-level effect of the filter is measured in F2.2.
