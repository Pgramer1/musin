## 1. Purpose

The graph layer is the contract between the Spark pipeline and everything after it: the Neo4j import (F3.4), the RQ3 analysis in Spark, and member B's GDS work. A silent error there, such as a duplicated edge, a dangling endpoint, a decade table that disagrees with the edges, or a primary genre that doesn't match the genre profile, would surface weeks later as a strange number in the report. F3.3 is an independent check suite that reads only the four written §8.1 tables. It covers FR-13 and the RULES §6 list, and it also guards against unexplained changes from one build to the next.

## 3. How it works

Every check counts **violating rows** (0 = pass). Conditions on one table are evaluated in a single aggregation pass. A null in a condition is treated as "not violated", except where null is itself the error: for example, a null weight counts as `weight_below_1`. The checks:

| Table | Checks |
|---|---|
| all four | `schema`: exact §8.1 names, order, types |
| `nodes_artist` | `null_artist_id`, `null_mbid_or_name`, `duplicate_artist_id`, `duplicate_mbid`, `below_min_recordings`, `node_without_edge` (§8.3), `excluded_artist_type` (D-021), `unknown_primary_genre`, `genre_votes_mismatch` (null exactly when there's no primary genre), `genre_votes_not_positive`, `primary_genre_not_top_share` |
| `edges` | `null_key`, `duplicate_key`, `self_loop`, `unknown_edge_type`, `co_credited_not_ordered` (§8.2 `src_id < dst_id`), `weight_below_1`, `year_null_mismatch`, `first_year_after_last`, `year_out_of_range` ([1877, snapshot year], D-023), `endpoint_not_a_node` |
| `edges_by_decade` | `null_key`, `duplicate_key`, `decade_not_multiple_of_10`, `weight_below_1`, `row_without_edge`, `invariant_decades_exceed_weight` (§8.1/D-011), `decade_outside_edge_years`, `dated_edge_without_decades`, `first_decade_mismatch`, `last_decade_mismatch` |
| `artist_genre` | `null_key`, `duplicate_key`, `share_out_of_range`, `shares_not_summing_to_1` (±1e-9), `unknown_parent_genre` (D-024 mapping), `artist_not_a_node` |
| run-to-run | rows of each table and edges per type, against the last passing check |

**Decade consistency is checked in a stronger form than §8.1 requires.** Both tables come from the same per-recording years (F3.1), which gives these rules:

- A dated edge's earliest decade row is the decade of `first_year`, and its latest is the decade of `last_year`.
- An undated edge has no decade rows.
- No decade row falls outside the edge's year span.

The §8.1 invariant (Σ decade weight ≤ edge weight) only catches decade weights that are too large. These rules also catch rows that are missing or shifted.

**Primary-genre consistency.** `nodes_artist.primary_genre` comes from `clean/artist_primary_genre` and `artist_genre` from `clean/artist_genres`. Both were made by F2.5, but they reach the graph by separate joins. The check recomputes the top share with the §8.1 tie-break (alphabetical) and requires equality, null-safe: an artist with a profile must have its top genre, and one without a profile must have null.

**Run-to-run ([D-030](../decisions.md#d-030--graph-quality-checks-run-to-run-tolerance-and-baseline)).**

- Each graph folder (full, and each sample fraction) keeps its own baseline in `_checks.json`: the counts of its **last passing** check.
- A new check fails if any table's row count, or any edge type's count, moved by more than `checks.max_row_change` (5 %) relative to that baseline. Per-type counts are included because a change in one type can hide inside the total, as the demonstration below shows.
- A deliberate change (a G1 decision, a new filter) is accepted with `--accept-changes`. The accepted names are recorded in `_checks.json` and must be explained in a decision entry.
- A failing check never overwrites the baseline, so it can't be "fixed" by re-running.

**Outputs.** `_checks.json` holds the time, commit, counts, per-table content fingerprints (as in F3.2), and every check result. F3.4 can use the fingerprints to refuse exporting a graph that differs from the last checked one. The Spark-side analyses can use them to state which graph a number came from. Spark ignores `_`-prefixed files, so `_checks.json` and `_manifest.json` can sit next to the tables.

*Rejected alternatives:*
- **Folding these checks into `graph.build`.** The build already has inline checks. An independent reader also catches what the build code cannot see: partial writes, files edited or copied by hand, a teammate's copy.
- **A fixed expected range per table.** Every G1 decision would need new ranges. A tolerance relative to the last accepted build follows the graph as it evolves.
- **Checking D-028 (one instance per recording and pair) here.** The graph tables no longer contain recording ids. That check stays inside F3.1, where the instances exist.

## 6. How to run

```bash
# after every full graph build (F3.1)
docker compose exec spark python -m musin.graph.build --config config/pipeline.yaml
docker compose exec spark python -m musin.graph.checks --config config/pipeline.yaml
# after a deliberate change (e.g. a G1 decision), once, and explain it in docs/decisions.md
docker compose exec spark python -m musin.graph.checks --config config/pipeline.yaml --accept-changes
# sample graphs: the F3.2 chain runs the checks itself
docker compose exec spark python -m musin.graph.sample --config config/pipeline.yaml --sample 0.05
```

Runtime on the reference machine: full graph **27–28 s**; the sample checks add a few seconds to the ≈ 95 s sample chain.

## 7. Verification and results

Runs on 2026-10-11, snapshot `20261007-002147`. The graph is the F3.1 build with D-028 (commit `2ac5547`).

**Full graph:** all **49 checks passed** in both runs (27 s, 28 s). Run 1 had no baseline ("no previous count") and created `_checks.json`. Run 2 compared against it with 0 % change on all eight counts. The full result is `reports/tables/graph_checks.csv`. Highlights:

- The §8.1 `edges_by_decade` invariant and its stronger first/last-decade form hold for all 3,541,659 edges and 3,829,423 decade rows.
- Every node has an edge, and every edge endpoint is a node.
- `primary_genre` equals the top `artist_genre` share, with the alphabetical tie-break, for all 1,180,939 nodes.

**Guard demonstration on real data** (sample graph 0.05; full data untouched):

| Step | Config | Result |
|---|---|---|
| 1 | committed config | exit 0; 49 checks passed; 310,253 nodes, 535,372 edges; baseline written |
| 2 | temporary copy with `max_credit_size: 20` | build: 311,849 nodes, 560,761 edges (+4.7 %, inside 5 %). Check: **`run_to_run.edges_CO_CREDITED` FAIL, 263,641 → 286,995 (+8.86 %)**, exit 1. Neither `_checks.json` nor `_manifest.json` was rewritten (unchanged timestamps) |
| 3 | committed config | exit 0; 49 checks passed; fingerprints identical to F3.2's (`edges` -728045217745244929017) |

Step 2 is the case per-type counts exist for: a change concentrated in one edge type stayed under the tolerance in the total. Step 3 also repeats F3.2's determinism result. The temporary config was deleted.

**Tests:** `pytest` 126 passed (110 earlier + 16 new cases from 8 test functions; the parametrised edge test gives 9 of them); `ruff check` / `ruff format --check` passed. The tests build one valid 3-artist graph, which passes all checks, and corrupt it one way at a time, asserting exactly which checks fire.

## 8. Known issues and limitations

- **Row-level, not semantic.** The checks prove the tables are internally consistent and follow the contract. They don't prove that edges mean what the PRD says; the F3.1 unit tests and cross-checks do that.
- **The tolerance is a heuristic.** 5 % catches accidental drops and filter changes, but a real error smaller than 5 % in every count would pass the run-to-run part. The structural checks still apply to it.
- **D-028 (one instance per recording and pair) cannot be checked here**, because the graph has no recording ids. F3.1 checks it during the build.
- **`--accept-changes` accepts every out-of-range count in that run.** Its use is recorded in `_checks.json` (`changes_accepted`), but the reason lives only in the docs.
