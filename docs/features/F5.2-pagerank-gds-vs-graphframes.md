## 1. Purpose

The architecture (PRD §7) splits the work: Spark builds the graph, and Neo4j + GDS run the graph algorithms. The obvious alternative is to stay in Spark and run the algorithms with GraphFrames, which would avoid the CSV export and the Neo4j import. FR-22 asks for the measurement that decides between them: PageRank on identical input in both engines, comparing runtime and top-100 overlap. If GraphFrames were about as fast and gave the same answer, Neo4j would be hard to justify (goal G4).

## 3. How it works

1. **Identical input** (D-042):
   - **Which graph.** Both engines read the graph named in `loaded_graph.json`.
   - **GDS** builds the F3.5 projection `collab_undirected`: one undirected relationship per artist pair, all four edge types merged.
   - **GraphFrames** reads that graph's `nodes_artist` and `edges` Parquet (the marker's `source`). It forms the same distinct unordered pairs and emits each in both directions.
   - **Check.** The report refuses to run unless every repetition of both engines saw the same node count and directed-edge count. Both had 1,135,461 nodes and 5,727,076 directed edges (2 × 2,863,538 pairs).
2. **Unweighted on both sides.** GraphFrames' `pageRank` has no weight parameter, so the comparison can't use F4.1's weighted PageRank (PRD §5.5). Both engines run plain PageRank:

   PR(v) = 0.15 + 0.85 · Σ PR(u)/deg(u) over v's neighbours.

   Both GDS and GraphX use this unnormalised form, in which scores sum to the number of artists. A test checks GraphFrames against a power-iteration reference. F4.1's weighted scores are added as a reference row, not as a contestant.
3. **Same settings and cores:**
   - damping 0.85 (GraphFrames reset probability 0.15);
   - both run to convergence at tolerance 1e-7, with GDS capped at 1,000 iterations;
   - 4 cores each. GDS Community Edition can't use more, so Spark gets `local[4]`.
4. **Phases.** Each repetition is timed in three phases with `time.monotonic()` in the Python process that drives the engine:
   - **load:** GDS builds the projection from the store, a Cypher aggregation over 3.08 M typed relationships. GraphFrames reads the Parquet, forms the pairs, then caches and counts vertices and edges.
   - **compute:** the PageRank call, until every score exists. For GDS that is `gds.pageRank.mutate`; GDS's own `computeMillis` is recorded too. For GraphFrames it is `pageRank(...)` plus caching and counting the result.
   - **output:** GDS streams 1.1 M scores to the Python client; GraphFrames writes them as Parquet.
5. **Memory and order:**
   - **GDS** runs first, with Neo4j up and Spark idle. All 3 repetitions run in one process, re-projecting each time.
   - **GraphFrames** runs next, with Neo4j stopped (RULES §10) and the normal 12 GB driver, each repetition in a fresh process (as D-041).
   - The scores of repetition 1 of each engine are compared.
6. **Comparison** (`compare`): Spearman ρ over all artists, the Jaccard overlap and intersection of the two top-100 sets (ties broken by artist id, as in F4.1), and absolute and relative score differences.

*Rejected alternatives:*
- **Weighted GDS against unweighted GraphFrames.** That would compare two different measures, not two engines.
- **GraphFrames' Pregel API with a custom weighted PageRank.** It would be our own algorithm rather than the library's, and slower still.
- **A fixed iteration count instead of a tolerance.** GDS needs 94 iterations here. Fixing the count would hide the fact that each engine decides convergence differently, and F4.1 runs to convergence too (D-033).
- **All cores for Spark.** That would compare 16 Spark threads with 4 GDS threads, a licence limit rather than an engine property.
- **Counting the Neo4j import in the GDS load.** The import happens once per graph build (F3.4: export about 25 s, import about 2 min on the full graph), while PageRank can run any number of times on it. It is reported separately (§7).

## 6. How to run

From WSL Ubuntu, repo root, after `docker compose build spark` (for the GraphFrames jars) and with the graph to compare loaded in Neo4j:

```bash
docker compose exec spark python -m musin.benchmark.pagerank --config config/pipeline.yaml --engine gds           # Neo4j running
docker compose stop neo4j
docker compose exec spark python -m musin.benchmark.pagerank --config config/pipeline.yaml --engine graphframes   # writes the report
docker compose start neo4j
```

Runtime on the reference machine (2026-10-20): GDS command 127 s, GraphFrames command 24.7 min (06:04:39–06:29:20 UTC; 3 × 470–563 s). There's no sample mode, because both commands use the loaded graph. Importing the sample graph would replace the full graph and its P4 write-backs.

## 7. Verification and results

**Environment:** the F5.1 machine and software ([`benchmark_environment.csv`](../../reports/tables/benchmark_environment.csv)): i5-13450HX, WSL2, Spark 3.5.9, Java 17. Neo4j 5.26.30 Community + GDS 2.13.12, heap 8 GB. GraphFrames 0.12.3. Graph `full`, edges fingerprint `-2227712706449027820962`.

**Checks (all passed):**
- **Same input:** 1,135,461 nodes and 5,727,076 directed edges in every repetition of both engines.
- **GDS converged** in 94 iterations every time.
- **Score sums ≈ N:** 1,135,459.6 for GDS and 1,135,461.0 for GraphFrames, as expected with no dangling nodes.
- **Stable repeats:** each engine's score sum is identical across repetitions (GDS to 13 significant digits).

**Runtime** (seconds, median of 3 with min–max; [`benchmark_pagerank_summary.csv`](../../reports/tables/benchmark_pagerank_summary.csv)):

| Phase | GDS | GraphFrames | GraphFrames ÷ GDS |
|---|---:|---:|---:|
| load | 11.8 (11.7–27.7) | 9.5 (8.1–9.9) | 0.81 |
| compute | **3.8** (3.8–4.1) | **469.7** (459.2–550.9) | **122.7** |
| output | 14.7 (14.6–14.8) | 2.4 (2.3–2.6) | 0.17 |
| total | 30.3 (30.1–46.4) | 482.1 (469.5–563.0) | 15.9 |

GDS's own `computeMillis` was 3.8–4.0 s, so the client-side compute time is almost all algorithm. The first GDS load (27.7 s) was slower than the next two (11.7–11.8 s), most likely because Neo4j's page cache was cold after the restart (not measured). The median absorbs this.

**What the numbers show:**

- **Both engines give the same answer.** The top-100 lists match exactly and ρ is 0.99999 over 1.1 M artists. The scores differ by one uniform factor: the median and maximum relative difference are both 1.218 × 10⁻⁶. GDS stops when every change is below 1e-7, slightly short of the fixed point (its scores sum to 1.4 less than N), while GraphX converges onto it. Ranks don't change except among near-ties, which is why ρ isn't exactly 1.
- **GDS computes PageRank about 120× faster** on the same 4 cores: 3.8 s against 470 s. Including load and output, a full PageRank costs 30 s in GDS and 8 min in GraphFrames (16×).
- **What GraphFrames saves doesn't pay for that gap.** It skips the Neo4j import, which happens once per graph build (F3.4: about 25 s export plus 2 min import), and its load and output phases are faster than GDS's (9.5 s against 11.8 s, and 2.4 s against 14.7 s, since GDS streams 1.1 M rows through Bolt). Even with the import counted, one GDS PageRank (about 3 min: 25 s export, 2 min import, 30 s run) is cheaper than one GraphFrames run (8 min), and F4.1/F4.2 run several algorithms on the same import. This supports PRD §7's split: Spark for ETL, GDS for algorithms.
- **Why GraphFrames is slow here:**
  - It runs PageRank through GraphX's Pregel, as many supersteps of distributed joins with shuffles.
  - With a tolerance, GraphX's dynamic variant keeps going until every vertex's change is below 1e-7.
  - GDS iterates over an in-memory compressed adjacency list on one JVM.

  The event logs in `$MUSIN_DATA/benchmark/pagerank/full/spark-events/` hold the per-stage breakdown; they weren't analysed further.
- **Weights matter more than the engine.** Unweighted PageRank shares only 72 of its top 100 with F4.1's weighted ranking (ρ 0.887). Springsteen drops from #1 to #20 without his live-archive weight, and the author Agatha Christie enters at #17 (presumably through audiobook credits; not checked). RQ4 keeps the weighted F4.1 results (PRD §5.5); this run only shows that the weighting is a substantive choice.
- **GraphFrames' spread:** its third repetition was 17 % slower (551 s against 459–470 s). That suggests background load on the host, as in F5.1's repetition 3; the median is robust to it.

**Tests:** 6 in `tests/test_benchmark_pagerank.py`. The full suite has 244 tests, all passing, and `ruff` is clean.

## 8. Known issues and limitations

- **Not F4.1's measure.** The comparison is unweighted because GraphFrames can't weight PageRank (D-042). A weighted comparison would need a custom Pregel implementation.
- **One machine, 4 cores, local mode.** GraphFrames is built for clusters, and on more machines its Pregel joins would parallelise further. GDS Community is limited to 4 cores. The result says which engine fits *this* project's single-machine setup, not which is faster in general.
- **Different convergence rules** (D-042) mean the two engines don't stop at the same point. Their scores differ by 1.2 × 10⁻⁶ relative, far below anything that changes a rank.
- **No iteration count for GraphFrames.** Its tolerance mode doesn't report iterations, so cost per iteration can't be compared.
- **The GDS output phase** measures streaming through the Python driver to a pandas frame. A pure in-database workflow (write-back, as F4.1 does) would cost differently.
- **The import is outside the GDS timings.** The F3.4 numbers quoted above come from F3.4 runs, not from this benchmark.
- **Run timestamps of the 2026-10-20 run are approximate.** The first version stamped `started_at_utc` when each run's record was written, after the timer had stopped. The stored value was renamed `finished_at_utc`, and `started_at_utc` was rebuilt as finished − `total_s`. For GraphFrames that is up to about 11 s too early, because the record was written after the score sum and Spark shutdown. The code now records both times directly. The phase timings are unaffected.
- **Disk:** `$MUSIN_DATA/benchmark/pagerank/full/` holds 3.3 GB (three GraphFrames score copies plus event logs). It can be deleted once the report is final.
