## 1. Purpose

PRD goal G4 asks us to justify the architecture with measurements, and FR-21 names the first one: how Spark's runtime responds to the data fraction (10 / 25 / 50 / 100 %) and the number of cores (1 / 2 / 4 / 8). The report uses it to answer two questions:

- Does local-mode Spark on one 24 GB machine handle the full MusicBrainz export in reasonable time?
- How much of that comes from parallelism?

Nothing in the pipeline could vary the core count before this feature, because `get_spark` always ran `local[*]`. The Spark event logs that NFR-04 asks for were also off.

## 2. What was built

| Piece | What it is |
|---|---|
| `python -m musin.benchmark.scaling` | Runs the grid `benchmark.scaling.{fractions × cores × repeats}`: one fresh process per cell, then the report tables and figure |
| `Cell`, `grid` | A cell is (fraction, cores, repeat). The grid is repetition-major and validated (fractions in (0, 1], integer cores ≥ 1, no duplicates) |
| `prepare_root`, `bench_config` | Scratch data root with relative symlinks to the real `raw/` and the four full artist tables. A config copy reads and writes there and sends report tables there too |
| `run_cell` | Times the four chain stages in this process at `local[<cores>]` and writes `runs/<cell>.json` atomically (stage seconds, Spark settings, every stage's counts) |
| `summary_rows`, `run_rows`, `environment_rows`, `plot` | Median, min and max per cell; speedup, efficiency and fraction-vs-full; machine and software details; the two-panel figure |
| `musin.common.spark.use_benchmark_settings` | Pins `local[n]` and turns on the event log for every later `get_spark()` in the process. Only the benchmark calls it, so pipeline stages are unchanged |
| Config | `paths.benchmark`, `benchmark.scaling.{fractions, cores, repeats}` (PRD §8.4, D-041) |
| `--fresh`, `--through-repeat N`, `--fractions/--cores/--repeats` | Start over, run only repetitions 1..N, or run a dev grid that writes to `$MUSIN_DATA/benchmark/dev/` |
| 18 tests | Grid order and validation, full vs sample mode per cell, scratch-root isolation (links, refusals, outputs never in real layers), summary maths, run rows, Spark settings, end-label spacing in the figure |

## 3. How it works

1. **Workload.** The four stages that read recordings: `clean.credits` (F2.2) → `clean.contributions` (F2.3) → `clean.years` (F2.4) → `graph.build` (F3.1). These are the stages `graph.sample` (F3.2) runs. The runner calls each stage's own `run(cfg, sample)`, including the stage's logging counts, so it times the real pipeline, not a copy of it. A fraction of 1.0 runs in full mode; smaller fractions run in sample mode (hashed `recording_id`, FR-12).
   - **Left out:** the F3.3 checks validate a build rather than produce it. The artist-level stages (F2.1, F2.5) don't depend on the fraction. Both would only add a constant.
2. **One process per cell.** The parent starts `python -m musin.benchmark.scaling --cell <f> <cores> <repeat>` for every unfinished cell. Each cell therefore starts from a cold JVM with no cached data, and `spark.driver.memory` (fixed when the JVM starts) is the same everywhere: `SPARK_DRIVER_MEMORY=12g`. Inside the cell, each stage starts and stops its own SparkSession as in production, and `use_benchmark_settings` keeps every one of them on `local[<cores>]`.
3. **Isolation.** The cell's config points at `$MUSIN_DATA/benchmark/scaling/data`, which holds relative symlinks to `raw/` and to `clean/{artists, special_artists, artist_genres, artist_primary_genre}`. All writes land next to those links: `clean/credits`, `graph/`, `sample/f<x>/…`, and, because `reports_dir` is redirected to an absolute path there, F3.1's `graph_build_summary.csv`. The real `clean/`, `graph/`, `sample/` and committed `reports/tables/` are never written. Tests check this for both modes.
4. **Timing.** Each stage is timed with `time.monotonic()` around its `run()`, so a stage's time includes starting its SparkContext, reading Parquet and writing its output, as a user sees it. The total is the sum of the four stages. JVM start-up and the settings snapshot fall outside the timer.
5. **Spark settings.** Only the core count changes. Everything else stays at the pipeline's defaults, recorded per cell: `spark.sql.shuffle.partitions` 200, AQE on (with partition coalescing). Tuning per core count would measure the tuning, not the scaling.
6. **Order and resume.** The grid runs repetition-major (all 16 cells, then again), so slow drift such as a warmer machine, a fuller page cache, or other work on the host hits every cell rather than one cell's three repeats. A finished cell's JSON is written via a temp file and rename, so a crash leaves no partial result. A re-run skips finished cells. The report is written only when all 48 cells exist.
7. **Summary.** Per fraction × cores:
   - `median_s`, `min_s` and `max_s` over the repetitions
   - `speedup` = median at 1 core / median
   - `efficiency` = speedup / cores
   - `vs_full` = median / median at 100 % with the same cores
   - the per-stage medians

*Rejected alternatives:*
- **Timing with `spark-submit` and the event logs alone.** Event logs measure per-job time, not stage boundaries as the pipeline defines them, and parsing them is more work for the same answer. They are kept for drill-down (NFR-04).
- **One JVM for the whole grid.** The core count is fixed per SparkContext and could be changed between sessions, but cached Parquet metadata and JIT warm-up would favour whichever cell runs later.
- **Writing into the real layers.** Fraction 1.0 would rewrite `clean/` and `graph/` 12 times and overwrite the committed `graph_build_summary.csv`. The output would be identical, but a crash mid-write would leave the pipeline broken.
- **Warm-up runs.** Every real pipeline run is a cold start, which is what the benchmark should measure.

## 6. How to run

From WSL Ubuntu in the repo root, with Neo4j stopped and the machine idle and awake:

```bash
docker compose stop neo4j
# dev grid (sample mode, ~6 min): everything under $MUSIN_DATA/benchmark/dev/
docker compose exec spark python -m musin.benchmark.scaling --config config/pipeline.yaml --fractions 0.01,0.02 --cores 2,4 --repeats 1
# config grid: 48 runs; resumes after an interruption
docker compose exec spark python -m musin.benchmark.scaling --config config/pipeline.yaml [--through-repeat 1] [--fresh]
```

Runtime on the reference machine: dev grid 4 cells, about 6 min. Config grid: 19,765 s (5.5 h) of measured runs. Repetition 1 took 6,438 s, repetition 2 6,440 s, and repetition 3 6,886 s. The runs were made 2026-10-19, 08:15–15:07 UTC, in two invocations (`--through-repeat 1`, then the rest).

## 7. Verification and results

**Environment** ([`benchmark_environment.csv`](../../reports/tables/benchmark_environment.csv)):
- **Machine:** Intel Core i5-13450HX (16 logical CPUs visible to WSL, 10 physical cores: 6 performance and 4 efficiency), 17.6 GiB in the WSL VM.
- **Software:** Linux 6.18 WSL2, Python 3.11.16, Spark 3.5.9 (local mode), OpenJDK 17.0.20.1.
- **Run:** driver memory 12 GB, snapshot `20261007-002147`, commit `5717fce`.

**Median runtime in seconds, with min–max over 3 runs** ([`benchmark_scaling_summary.csv`](../../reports/tables/benchmark_scaling_summary.csv)):

| Fraction | 1 core | 2 cores | 4 cores | 8 cores |
|---:|---:|---:|---:|---:|
| 10 % | 334 (329–342) | 192 (186–198) | 137 (137–145) | 123 (114–127) |
| 25 % | 531 (526–531) | 292 (290–297) | 203 (191–230) | 191 (161–193) |
| 50 % | 745 (741–796) | 427 (421–431) | 302 (301–352) | 265 (224–292) |
| 100 % | 1,224 (1,190–1,333) | 680 (662–744) | 461 (459–546) | 385 (361–420) |

**Speedup over 1 core (efficiency):**

| Fraction | 2 cores | 4 cores | 8 cores |
|---:|---:|---:|---:|
| 10 % | 1.74 (0.87) | 2.43 (0.61) | 2.73 (0.34) |
| 25 % | 1.82 (0.91) | 2.61 (0.65) | 2.78 (0.35) |
| 50 % | 1.74 (0.87) | 2.47 (0.62) | 2.81 (0.35) |
| 100 % | 1.80 (0.90) | 2.66 (0.66) | 3.18 (0.40) |

![Spark scaling](../../reports/figures/benchmark_scaling.png)

**What the numbers show:**

- **The full export takes 6.4 min on 8 cores** and 20.4 min on one, so the whole recording chain fits comfortably on the reference machine. That supports the PRD §7 choice of local-mode Spark on one machine over a cluster.
- **Scaling is good to 2 cores and flattens after 4.** Efficiency is 0.87–0.91 at 2 cores, 0.61–0.66 at 4 and 0.34–0.40 at 8. Fitting Amdahl's law to the full-fraction medians gives an apparent serial share of 11 % (2 cores), 17 % (4) and 22 % (8). It rises with the core count, so plain serial code is not the whole story. Likely contributors:
  - each stage's own driver work (SparkContext start, Parquet footer reads, the logging `count()`s)
  - the 200-partition default shuffles
  - memory bandwidth shared by the cores
  - beyond 6 cores, the i5's efficiency cores

  These are hypotheses that the event logs could test; the benchmark doesn't separate them.
- **Larger inputs scale better at 8 cores**: 3.18× at 100 % against 2.73× at 10 %. There's more parallel work per fixed overhead.
- **Runtime is linear in the fraction, with a large fixed part.** A least-squares line through the four medians per core count fits with R² ≥ 0.98. The intercept is 261 s at 1 core and 110 s at 8, which is 21–29 % of the full runtime. That fixed cost is why the 10 % sample takes 27–32 % of the full time. Sample mode samples by hashed `recording_id` **after** reading the raw tables, so every fraction still scans the whole raw layer (D-041 consequences). The fraction axis therefore measures processing volume more than I/O volume.
- **Where the time goes** (full graph, medians): `clean.years` and `graph.build` together take 73–80 % at every core count. That's 467 s + 480 s of 1,224 s at 1 core, and 129 s + 151 s of 385 s at 8. They're the stages with the large joins: track → medium → release → country dates, and the pair self-join. They also scale best from 1 to 8 cores: 3.6× (years) and 3.2× (build), against 2.6× for credits and 2.8× for contributions.

**Run-to-run spread** (max / min − 1 per cell):
- **Tight:** at most 7.4 % in 7 of 16 cells, mostly 1–2 cores at the smaller fractions.
- **Wider:** 11–31 % in the other 9, mostly 4–8 cores. The largest are 50 % on 8 cores (224–292 s), 25 % on 4 cores (191–230 s) and 100 % on 4 cores (459–546 s).
- **Repetition 3** was 7 % slower in total and was the slowest run in 6 of those 9 cells. Background load on the Windows host is the likely cause.

More cores leave less idle capacity to absorb other work on the host, so the multi-core cells vary most. That's why the summary uses the median and the figure shows min–max bars.

**Interruption.** During repetition 3 the host slept for about 70 min while cell `f0.1_c2_r3` was in `clean.years`. `time.monotonic()` doesn't advance while the VM is suspended, so the cell measured 197.8 s against 192.0 and 185.8 s in the other repetitions. The stage was 78.1 s against 72.6 s in repetition 2. The cell was kept: only the log's wall-clock timestamps show the gap.

**Tests.** 18 tests in `tests/test_benchmark_scaling.py`; the full suite has 238 tests, all passing, and `ruff` is clean.

**Dev grid** (1 %/2 % × 2/4 cores, 1 repetition, 2026-10-19): 75–105 s per cell. It confirmed the end-to-end path (links, sample-mode outputs, event logs, tables, figure) before the config grid.

## 8. Known issues and limitations

- **One machine and one OS stack.** WSL2 inside Windows 11 shares the CPU with the host, and the host wasn't fully idle (repetition 3). The numbers describe this laptop, not Spark in general.
- **8 cores is not 8 equal cores.** On the i5-13450HX, Linux may schedule onto efficiency cores past the 6 performance cores. The 8-core point mixes core types.
- **The fraction axis isn't pure data volume.** Every fraction scans the full raw layer (§7). A benchmark of pure volume would need pre-sampled raw tables, which the pipeline doesn't have.
- **Default Spark settings only.** 200 shuffle partitions is too many for 1 core and maybe too few for full data at 8 cores. Tuned settings could shift the curve, but that is not what FR-21 asks.
- **Stage times include each stage's logging counts**, as in production. Some are extra Spark jobs, so the chain does more work than a minimal pipeline would.
- **Disk:** the scratch root keeps 1.4 GB of the last cells' outputs and 4.9 GB of event logs in `$MUSIN_DATA/benchmark/scaling/`. Both can be deleted once the report is final; the run JSONs are 48 small files.
