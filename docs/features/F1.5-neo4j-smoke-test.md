## 1. Purpose

The real graph reaches Neo4j only in P3 (sample graph by M2, Oct 19), but member B has to start the analysis code now (PRD §13 risk "Member B idle waiting for data"). Several things could go wrong on that path that have nothing to do with the data: the §8.3 CSV headers, `neo4j-admin` inside Docker, Community Edition limits, how GDS projects the four edge types, and whether the GDS algorithms compute what PRD §5.5 says they compute. This feature runs that whole path on a 12-artist toy graph whose answers are known, and checks GDS against an independent plain-Python implementation. Each problem is found on a 30-second run instead of on the full graph.

## 3. How it works

### 3.1 The toy graph

Two clusters: `rock` (artists 101–105) and `hip hop` (107–112). They are joined only through artist **106** (genre shares 0.5 / 0.5, so primary genre `hip hop` by the §8.1 alphabetical tie-break). The fixture also covers the cases most likely to break on real data:

- **Parallel and reverse edges.** 108–109 has `CO_CREDITED` and `FEATURED` (109 → 108). 101–103 has `CO_CREDITED` 101 → 103 plus `PERFORMED_FOR` **103 → 101**, so the pair appears in both directions.
- **Empty fields.** Artist 105 has no `areaName` or `beginYear`; edge 101–105 has no years.
- **CSV quoting.** Names `Foxtrot "The Bridge"` and `Juliet Rap, Jr.`
- **An unused genre.** `electronic` has a single artist share.

### 3.2 Import

`neo4j-admin database import full neo4j --overwrite-destination=true --nodes=… --relationships=…`, run as `docker compose run --rm --no-deps neo4j …` while the `neo4j` service is stopped. The one-off container uses the same image, volumes, and user, so the store ends up owned by UID 7474 and the server starts on it directly. Findings:

- **The database name must come first.** `--nodes`/`--relationships` are greedy, and the first attempt failed with `File 'neo4j' doesn't exist` because the trailing `neo4j` was read as a CSV file.
- **`artistId:ID(Artist)` imports as a STRING.** PRD §8.3 requires an integer. A run with the exact §8.3 header gave `valueType(a.artistId) = "STRING NOT NULL"` for all 12 artists. The global `--id-type=integer` can't be used, because `Genre` IDs are names. The per-group override **`artistId:ID(Artist){id-type:long}`** gives `INTEGER NOT NULL`, and the toy fixture uses it. PRD §8.3 had left this importer choice to F3.4. It changes the contract's header text, so it was approved and recorded as [D-016](../decisions.md#d-016--artistid-imported-as-an-integer-via-id-typelong), and §8.3 now carries the override.
- Empty fields become *missing* properties (not `""` or `0`), and quoted names survive.

### 3.3 Projections

**`collab_undirected`** is the COLLAB projection (PRD glossary). It is a Cypher-aggregation projection: each edge's endpoints are put in `artistId` order, weights are summed per pair, and the result is projected with `undirectedRelationshipTypes: ['*']`. That gives one undirected relationship per artist pair whatever the edge types and directions.

This is now the COLLAB definition ([D-017](../decisions.md#d-017--collab-projection-one-relationship-per-artist-pair-weights-summed)); F3.5 builds the production projection the same way.

*Rejected:* a native projection of the four types with `orientation: 'UNDIRECTED'` (`collab_native`, still built in the test for comparison). It keeps 22 parallel relationships instead of 19 pairs. Weighted degree is the same, but **betweenness changes**: GDS counts parallel edges as separate shortest paths. On the toy graph 108's score rises from 17.5 to 20.3 and 107's falls from 8.0 to 5.2, which the multigraph reference reproduces exactly. Native aggregation (`aggregation: 'SUM'`) would not help either, because it merges only within one type and one direction.

### 3.4 Checks against an independent reference

`reference.py` reads the same CSVs that were imported and computes each answer in plain Python:

| Measure | Reference formula | GDS call (PRD §5.5 settings) |
|---|---|---|
| Weighted degree | sum of merged pair weights | `gds.degree`, `relationshipWeightProperty: weight` |
| PageRank | PR(v) = (1 − d) + d · Σ PR(u) · w(u,v) / W(u), iterated to Δ < 1e-10, not normalised | `gds.pageRank`, damping 0.85; once to convergence, once with `max_iterations` 20 |
| Betweenness | Brandes, unweighted, each unordered pair once; parallel edges multiply path counts | `gds.betweenness`, unweighted, `samplingSize` 10,000, `samplingSeed` 42 |
| Louvain | Newman weighted modularity of the partition GDS returns | `gds.louvain`, weighted, concurrency 1 and 4, 3 runs each |
| Shortest path | BFS hops | Cypher `shortestPath` over all four types |

So the test doesn't depend on numbers typed in by hand. A wrong formula on either side, such as normalised PageRank, doubled undirected betweenness, or weights read as distances, shows up as a mismatch.

**Louvain expectation, corrected during development.** The first version expected exactly two communities (rock / hip hop) and failed: GDS returned four, `[101,102,103] [104,105,106] [107,108,109,112] [110,111]`. Their modularity, 0.475962, is higher than either plain genre split (0.460799 with 106 in rock, 0.433247 in hip hop), so GDS was right and the test was wrong. The checks now require what Louvain actually guarantees on this graph: no community mixes the two genre clusters, the modularity equals the reference, and it is at least the best genre split.

## 6. How to run

```bash
# from WSL, repo root. Replaces the graph in the `neo4j` database with the toy graph.
bash neo4j/smoke/run_smoke.sh --overwrite
# checks only, if the toy graph is already loaded:
docker compose exec spark python -m musin.neo4j_smoke --config config/pipeline.yaml
```

There is no sample/full distinction: the input is the fixed toy graph. Runtime on the reference machine: **30–31 s** end to end (import 0.7 s, Neo4j start until Bolt answers about 16 s, checks 19.5 s). After changing `docker-compose.yml`, recreate the Spark container once (`docker compose up -d spark`) so it gets `NEO4J_URI`.

## 8. Known issues and limitations

- **Contract change awaiting the second member's sign-off.** D-016 (the `{id-type:long}` artist header) was approved by the member running F1.5. The contract is still draft v1 until M1 (Oct 13), when both members sign it off (PRD §8 status).
- **COLLAB build cost is untested at scale.** D-017's Cypher-aggregation projection is slower to build than a native one; on the full graph F3.5 must run `.estimate` and record the build time.
- **PageRank at 20 iterations did not converge** on the toy graph (ranking unaffected). F4.1 should log `ranIterations` / `didConverge` on the real graph and report them.
- **Louvain concurrency is not in config.** PRD §5.5 asks for "fixed concurrency", but there is no `analysis.louvain_concurrency` key. The toy graph is deterministic at 1 and at 4, but 12 nodes prove nothing about non-determinism on 900 k nodes. F4.2 should add the key.
- **Community Edition, one database:** the smoke test overwrites whatever graph is loaded, hence the mandatory `--overwrite` flag. Re-import the sample or full graph afterwards (F3.4).
- **Toy scale says nothing about memory or speed.** `.estimate` returning bytes only proves the procedures run; the real estimate belongs in F3.5/F4.1 (RULES §7).
- `neo4j-admin` reports "Peak memory usage: 1.004GiB" even for 15 nodes. It sizes its own heap, separately from the server heap, so it must not run while Spark is busy.
- The smoke constraints (`smoke_*`) live in the toy database only; the production constraints are F3.5's `neo4j/01_constraints.cypher`.
