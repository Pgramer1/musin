## 1. Purpose

PRD §5 asks for RQ1's bridge table and RQ4's top-20 lists also "from a graph built with `Character` artists included" ([D-021](../decisions.md)). Gate G1 may add a classical-included run the same way. The pipeline could hold only one graph per mode: one `graph/` folder, export names `full` and `sample-f<x>` ([D-031](../decisions.md)), and P4 tables written by graph name. Rebuilding with a flipped filter would therefore overwrite the main graph, its F3.3 baseline, its export, and, on the full graph, the committed `reports/tables/`. F4.7 lets a *variant* graph be built, checked, exported, loaded and analysed next to the main graph, with no edit to `pipeline.yaml` and no risk to main results.

## 2. What was built

- A new top-level config key `variants` in `config/pipeline.yaml`, with the first variant `characters: {filters: {exclude_artist_types: []}}` (PRD §8.4, [D-035](../decisions.md)).
- `load_config(path, variant=name)`: validates the overrides and applies them on top of the main config. `Config.variant` and `Config.overrides` record them.
- `--variant <name>` on `musin.graph.build`, `musin.graph.checks` and `musin.export.neo4j_csv`.
- Variant-aware paths and names in `musin.common.layers`:
  - `layer_path` moves only the graph layer.
  - `graph_name` / `parse_graph_name` give `<base>-<variant>`.
  - `results_dir` (moved here from `musin.analytics.common`, which re-exports it) routes the tables of every graph.
- `neo4j/import_graph.sh` and `musin.export.neo4j_check --graph` accept variant names.
- `_checks.json` and `_export.json` record `variant` and `variant_overrides`.
- 12 unit tests in `tests/test_variants.py`.

## 3. How it works

1. **A variant is the main config plus a few filter overrides.** `variants.characters.filters.exclude_artist_types: []` is flattened to `{"filters.exclude_artist_types": []}` and written into a deep copy of the config. Every stage reads settings with `cfg.get()` as before, so no stage has to know about variants to apply the overrides.
2. **Only F3.1 filters may be overridden:** `exclude_artist_types`, `include_classical`, `min_recordings`, `max_credit_size` (`VARIANT_KEYS`). These are applied when edges are built (D-021 §2, [D-026](../decisions.md)), and credit size counts Character artists whatever the filter (D-026 §1). A variant can therefore read the main `clean/` layer as it is, and only F3.1 onward re-runs. `load_config` fails loudly if a variant:
   - is undefined, or has a name that isn't `[a-z][a-z0-9_]*`
   - sets any other key (e.g. `analysis.random_seed` or `filters.special_artists_file`, which F2.1 applies)
   - changes a value's type
   - changes nothing at all
3. **Paths.** `layer_path(cfg, "graph", sample)` appends `variants/<name>/` to the base (`$MUSIN_DATA` or `$MUSIN_DATA/sample/f<x>`). `layer_path(cfg, "clean", sample)` is unchanged, so the variant shares the main clean inputs. Putting a sample variant under its sample tree (rather than `variants/<name>/sample/...`) keeps everything derived from one sample in one place, as D-019 does.
4. **Names.** `graph_name(sample, variant)` = `full` | `sample-f<x>`, plus `-<variant>`. The name is used for:
   - the export folder `import/<name>`
   - the import script argument and the `loaded_graph.json` marker
   - the `graph` column that F4.1 and F4.2 stamp on every table

   The grammar is unambiguous because `sample-f<x>` contains no hyphen after the `f`, and variant names must start with a letter.
5. **Results.** `results_dir(cfg, name)` sends tables to:
   - `full`: `reports/tables/` (unchanged)
   - `full-<v>`: `reports/tables/variants/<v>/`
   - `sample-f<x>`: `$MUSIN_DATA/sample/f<x>/reports/tables/` (unchanged)
   - `sample-f<x>-<v>`: `$MUSIN_DATA/sample/f<x>/variants/<v>/reports/tables/`

   F3.1's `graph_build_summary.csv` and F3.3's `graph_checks.csv` use the same function. Before F4.7 they wrote to `reports/tables/` whenever `--sample` was absent, so a full variant build would have overwritten the main graph's report tables.
6. **P4 stages are unchanged.** They analyse whatever graph `loaded_graph.json` names (D-031) and route their tables by that name. A sensitivity run is: build → checks → export → import the variant → P4 stage → re-import the main graph.
7. **Run-to-run checks.** The F3.3 baseline is per graph folder ([D-030](../decisions.md)), so a variant has its own. Its first check passes with "no previous count", and later rebuilds of the variant are compared with the variant.

**Alternatives rejected** ([D-035](../decisions.md)):
- *Separate overlay files* (`config/variants/*.yaml`): PRD §8.4 keeps every result-changing setting in `pipeline.yaml`.
- *`--set key=value` on the command line*: a result-changing setting would then be recorded in no file.
- *Editing `pipeline.yaml`, rebuilding, and reverting*: overwrites the main graph and its reports, and is error-prone with two people.
- *A filename suffix* (`centrality_top_characters.csv`) instead of a folder: a folder keeps file names identical across graphs, so the same comparison code reads both.

## 5. Configuration

| Key (`config/pipeline.yaml`) | Value used | Meaning |
|---|---|---|
| `variants.characters.filters.exclude_artist_types` | `[]` | the `characters` variant keeps `Character` artists (main graph: `[Character]`, D-021) |
| every other key | main config | a variant inherits everything it doesn't override |

## 6. How to run

```bash
# 1. build, check and export the variant (Spark; sample ~1.6 min)
docker compose exec spark python -m musin.graph.build --config config/pipeline.yaml --sample 0.05 --variant characters
docker compose exec spark python -m musin.graph.checks --config config/pipeline.yaml --sample 0.05 --variant characters
docker compose exec spark python -m musin.export.neo4j_csv --config config/pipeline.yaml --sample 0.05 --variant characters
# 2. load it (replaces the loaded graph), analyse, and load the main graph again (WSL)
bash neo4j/import_graph.sh sample-f0.05-characters --overwrite
docker compose exec spark python -m musin.analytics.centrality --config config/pipeline.yaml
bash neo4j/import_graph.sh sample-f0.05 --overwrite
# full mode: the same commands without --sample, and graph names full-characters / full (ask first)
```

The clean layer of the base must exist: `musin.graph.sample --sample 0.05` (F3.2) for a sample variant, or the full P2 stages for a full one. Runtime on the reference machine (sample): build 53 s, checks 23 s, export 21 s, import with verification 84 s, F4.1 852 s, re-import of `sample-f0.05` 75 s. The full variant has not been run.

## 8. Known issues and limitations

- **Provisional graph.** The full variant uses the pre-G1 filters. After G1, rebuild it (`--variant characters`) and re-run F4.1/F4.3 on it before the main graph's P4 stages.
- **Memory:** build the full variant with Neo4j stopped. The first attempt on 2026-10-12, with Neo4j running, was OOM-killed (Spark 12 GB + Neo4j 13 GB > WSL 18 GB).
- **A variant run costs the main graph its write-back properties:** each import replaces the database, so re-run F4.1/F4.2 on the main graph after a sensitivity run if the demo needs them.
- **Only F3.1 filters can vary.** A variant that needs different `clean/` data (e.g. OD7 `use_release_level_credits`, or a different special-artist list) would need variant-aware clean stages; that is out of scope.
- **Neo4j still holds one graph.** A sensitivity run replaces the loaded graph for its duration, so it must be coordinated with anyone running P4 stages. `check_still_loaded` (F4.2) makes a stage discard its results if an import happens mid-run. Re-import the main graph afterwards.
- **No sample-vs-full comparison or manifest for variants.** `musin.graph.sample` (F3.2) only builds main sample graphs. A variant is identified by the fingerprints in its `_checks.json` and in `loaded_graph.json`.
- **`gds_projections.csv`** (F3.5) is still written only for the main full graph. A full variant's projection checks run but are not saved as a table.
