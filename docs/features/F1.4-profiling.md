## 1. Purpose

Before scoping the graph at gate G1 (Oct 16), we need measured facts about the dump: how complete the fields are that the research questions depend on, how large credits get, how sparse tags and contribution credits are, and which artists would become hubs. This feature produces those numbers from `raw/` as committed tables and figures, so every G1 decision can cite a file instead of a guess.

## 2. What was built

- `python -m musin.profiling`: one Spark job that writes 12 CSVs to `reports/tables/profile_*.csv` and 3 figures to `reports/figures/profile_*.png`. `--sample <fraction>` profiles a deterministic subset of recordings and writes to `$MUSIN_DATA/tmp/profiling_sample/`, so a sample can never overwrite report numbers.
- `musin.profiling.metrics`: pure transformations (credit sizes, credit pairs, featuring detection, release/recording first year, genre-tag matching, size histogram, null profile), each documenting its input and output columns.
- `musin.common.sampling.sample_by_hash`: deterministic sampling by `xxhash64(id)`. F3.2 (FR-12) will reuse it.
- `musin.profiling.figures`: static matplotlib figures in the project chart style.
- Config: new `profiling:` section ([D-015](../decisions.md#d-015--profiling-report-parameters-and-definitions)). 9 new tests.

## 3. How it works

All metrics read `raw/` only. The report collects nothing that isn't already aggregated: histograms, top-k lists, and one row per table for null counts. Definitions are fixed in D-015; the main ones:

- **Credited artist**: appears in the `artist_credit_name` of at least one recording's credit. **Credit size** = distinct artists in that credit. **Pair-instances** = n(n−1)/2 per recording, the number of artist pairs a recording would contribute before any filter.
- **Featured artist**: comes after a join phrase matching `credits.featuring_pattern`. A credit "has featuring" when a non-final position's join phrase matches (PRD §8.2).
- **First release year**: earliest `date_year` over `release_country` ∪ `release_unknown_country`, across every release containing the recording (via track → medium → release). This previews FR-07; F2.4 implements it for real.
- **Genre tag**: a tag whose name matches an official `genre.name` or `genre_alias.name`, case-insensitively, with vote count > 0. Coverage is reported at artist level (`artist_tag`), at release-group level (the artists credited on a tagged release group), and for either source. An **appearance-weighted** version counts each (recording, artist) appearance, which shows how much of the *activity*, not of the artist list, is labelled.
- **Contributions**: the `contributions.produced_for` / `performed_for` allowlists matched against artist → recording link types. For OD7, the same names on artist → release link types, mapped to recordings through their tracks.
- **`min_recordings` grid (OD2)**: distinct credit pairs from credits with at most `max_credit_size` artists, kept when both artists have ≥ t recordings. This is a **preview** before the F2/F3 filters (special artists, band members, contribution edges), not the final graph size.
- **Classical (OD1)**: artists with a positive artist-level `classical` tag. Sub-genres such as `opera` or `baroque` are not included, so this is a lower bound.

*Rejected:* computing the profile in a notebook. RULES §8 keeps logic out of notebooks, and G1 needs one reproducible command. *Rejected:* profiling a 5% sample only. The sample run showed artist-level shares are biased by recording sampling (artist-level genre coverage 18.9% in the sample against 9.9% in full, because sampled recordings over-represent prolific, well-tagged artists), so the report uses the full data.

## 6. How to run

```bash
docker compose exec spark python -m musin.profiling --config config/pipeline.yaml --sample 0.05   # dev, writes to $MUSIN_DATA/tmp/
docker compose exec spark python -m musin.profiling --config config/pipeline.yaml                 # full, writes reports/
```

Runtime on the reference machine: sample 5% **185 s**, full **383 s** (397 s wall time).

## 8. Known issues and limitations

- **The OD2 grid is a preview:** credit pairs only, before special-artist, band-member, and contribution handling. The real counts come from F3.1.
- **Classical is a lower bound:** only the literal `classical` artist tag counts; sub-genre tags and release-group tags are ignored here.
- **Genre matching is name-based:** a tag counts if its name equals a genre or alias name. Misspellings or other wording ("hiphop") are not matched; that is F2.5's job.
- **Sample-mode bias:** sampling recordings biases artist-level shares upwards (§3). Use `--sample` for development only.
- **Recording-level contribution coverage reflects documentation effort,** not real production practice (PRD §6.3).
- **Release years contain errors** (years 206 … 3030); they are reported, not fixed, here.
